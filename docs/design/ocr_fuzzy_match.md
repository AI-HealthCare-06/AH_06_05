# 약 이름 "비슷한 이름 추천" (자모 3글자 조각 유사도 — 멘토링 4회차 "PG n-gram으로 먼저, 임베딩은 검색 알고리즘")

`app/services/ocr/matcher.py` (`NameMatcher.similar`) · 연결은 `pipeline.read`.

## 무엇을, 어떻게, 왜

| 질문 | 답 |
|---|---|
| 무엇을 | OCR이 읽은 약 이름이 급여목록(22,045품목)에서 **규칙으로 안 찾아질 때**, 글자 하나가 바뀌거나 빠진 이름의 정답 후보를 올린다 |
| 어떻게 | 이름을 **자음 · 모음(자모)으로 풀어** 3글자 조각으로 자르고, 조각 모음의 겹침 ÷ 합침(자카드)이 `OCR_SIMILAR_MIN`(0.70) 이상인 상위 3개를 **사용자가 고르는 후보**(needs_confirm)로만 올린다. 자동 확정은 하지 않는다 |
| 왜 이 방식 | ① 멘토님: 약 이름 맞추기는 벡터 DB가 아니라 PG n-gram으로 먼저. 계산은 PostgreSQL `pg_trgm`의 `similarity()`와 **같다**(실제 pg_trgm과 400쌍을 대조해 모두 같은 값). ② 자모로 풀면 글자 하나가 비슷한 글자로 읽혀도(엘→멜) 조각 대부분이 남는다 |
| 임베딩은? | 이 단계에는 쓰지 않는다. 약 이름은 글자 모양이 틀리는 문제라 뜻을 비교하는 임베딩보다 글자 조각이 맞고, 설명 가능하며(왜 이 후보인지 점수로 보임) 비용이 없다. 임베딩은 의미 검색(복약 안내 RAG)에 쓴다 |

처리 순서: 규칙(제조사 떼기 · 2글자 조각, 0.90↑ 확정) → **이 추천** → (그래도 못 찾으면) LLM 후보정(`ocr_llm_fix.md`).
추천 결과는 LLM 추천과 같은 방식으로 사용자가 고르는 단계로 간다 (후보 점수는 원래 규칙 점수가 아니라 이 유사도).

## 왜 음절이 아니라 자모, 왜 0.70인가 (10/14 측정)

**실제 CLOVA 결과 86줄에서 규칙이 못 찾은 줄**(5줄) 중 정답이 목록에 있는 2줄:

| 읽은 이름 | 음절 3글자 조각 | **자모 3글자 조각** |
|---|---|---|
| `엘로시드캡슬7.5mg(엘록시캄)` (정답 멜로시드캡슐 · 멜록시캄) | 0.38 | **0.71** |
| `아스피린프로택트쟁100밀리그람` (정답 아스피린프로텍트정) | 0.55 | **0.71** |
| `라니티딘` (급여목록에 없는 약) | 0.18 | 0.29 → 추천 없음 |
| `허말론침안액…` (너무 많이 깨짐) | 0.29 | 0.48 → 추천 없음 |

**오타 시뮬레이션** (급여목록에서 100개 이름 × 5종류, 규칙이 못 찾은 350개): 오타 모양은 실제 CLOVA에서 본 것(글자 하나가 비슷한 글자로 · 글자가 빠짐 · `밀ㄹ그램`처럼 낱자모가 끼어듦)을 본떴고, 2글자 동시 오류(`jamo2`, `blur2`)는 일부러 더 심하게 만든 최악 경우다.

| 단계 | 개수 |
|---|---|
| 규칙만으로 바르게 찾음 / 후보에 정답 | 130 / 17 (29%) |
| 규칙이 못 찾은 350개 중 **추천 1번이 정답** | **252 (72%)** |
| 추천 2~3번에 정답 | 4 (1%) |
| 추천은 나왔지만 정답 없음 | 3 (1%) |
| 추천 없음 → LLM으로 | 91 (26%) |

→ 규칙+추천으로 오타의 약 81%(403/500)가 정답 후보에 오른다 (규칙만: 29%). 규칙이 못 찾은 것 중 종류별 추천 1번 정답률: 글자 하나 바뀜 95%, 낱자모 끼어듦 98%, 글자 빠짐 86%, 2글자 바뀜 70%, 2글자가 완전히 다른 글자로(흐림) 36%.

**기준값 선택**: `OCR_SIMILAR_MIN`을 바꿨을 때(자모, 다른 시뮬레이션 219개 · 목록에서 뺀 약 250개):

| 기준 | 추천이 나온 오타 (그중 정답 없는 추천) | 목록에서 뺀 약에 다른 약이 추천되는 비율 |
|---|---|---|
| 0.60 | 196 / 219 (89%) (5) | 39% |
| **0.70** | **170 / 219 (78%) (2)** | **21%** |
| 0.75 | 143 / 219 (65%) (2) | 11% |
| 0.80 | 115 / 219 (53%) (1) | 6% |

점수가 0.71인 실제 오독 2건을 잡는 선이라 0.70으로 골랐다. 더 높이면 실제 오독을 놓치고, 낮추면 오타를 더 잡지만 엉뚱한 약 추천이 늘어난다.

## 정직한 한계

- **소리가 비슷한 다른 약은 오타와 글자만으로 구별할 수 없다.** 목록에서 약 하나를 빼고(같은 성분 · 같은 상표 제외) 그 이름을 그대로 물으면 약 21~22%에서 비슷한 이름의 다른 약이 추천된다. 처방전에 급여목록에 없는 약이 적히는 일은 드물고(실제 9장에서는 `라니티딘` 1줄), 그 경우에도 추천은 **사용자가 고르는 후보일 뿐 자동 확정이 아니다**. 급여목록에 없는 실제 약 12개 · 처방전 문구 10개 · 무작위 글자 50개로 시험했을 때는 추천이 0건이었지만, 12개는 적은 표본이다.
- 그래서 화면은 후보를 고르게 할 때 **제품명 전체**(성분 · 함량 포함)를 보여 주고, 원본 글자와 나란히 보여 줘야 한다 (사용자가 1번 후보를 무심코 누르지 않게). 후보 목록에는 현재 "추천에서 온 후보"라는 표시가 저장되지 않는다 (필요하면 항목에 칸 추가). 저장되는 `match_score`도 이 유사도(0.70~1.0)라서, 화면에서 "확실도"처럼 보여 주면 안 된다 — needs_confirm 상태가 "확인 필요"를 뜻한다.
- 오타 시뮬레이션은 시뮬레이션이다. 실제 CLOVA 오독 표본은 9장(오독 줄 5개)뿐이라, 실제 사진이 모이면 같은 도구로 다시 재서 기준을 조정한다.
- 비용 (10/14 측정): 급여목록 조각 색인이 메모리를 약 44MB 더 쓰고 (처음 한 번 0.56초에 만듦), 못 찾은 줄 1개당 약 90ms가 든다. 규칙이 찾은 줄에는 쓰지 않는다.
- PostgreSQL이 아니라 같은 계산을 Python에서 한다. DB의 문자 분류 설정(`lc_ctype`)이 `C`이면 pg_trgm이 한글에서 조각을 하나도 만들지 못하는 것을 확인했다 (`C.UTF-8` · `en_US.UTF-8`은 정상) — DB 설정에 따라 결과가 달라지지 않게 하려는 선택이다. 품목이 훨씬 많아지면 `pg_trgm` GIN 색인으로 옮길 수 있다 (한글을 자모로 푼 칸을 따로 두고, 계산은 같다).

## 다시 재는 방법

레포 루트에서 `uv run python eval_llm_typos.py` (돈 · 키 없음, 규칙+추천 결과와 음성 대조를 출력). `OCR_SIMILAR_MIN`은 환경변수로 바꾸고 0이면 추천을 끈다.
