# 임베딩 한 장 (무엇을, 어떻게, 왜)

10/16 작성. 10/14 회의 5번과 멘토링 4회차 "임베딩 차원 수, 임베딩할 데이터, Top-K 후 후보정"에 대한 답이다. 설계만 있고 코드는 아직 없다.

숫자는 두 가지 방법으로 얻었다. 개수와 글자 수는 허가정보 DB 전체(21,924행)를 안내문 근거 선택 규칙으로 전부 세었다. 토큰 수는 무작위 300개 허가번호 표본(문장 14,810개)을 cl100k 토크나이저로 세어 글자당 토큰 비율을 구한 뒤 전체에 곱했다. 비용과 점수 기준은 OpenAI 키가 이 작업 환경에 없어 실제 호출로는 재지 못했다.

## 한눈에

| 질문 | 답 |
|---|---|
| 무엇을 | 챗봇의 자유 질문에서 답의 근거가 될 글을 찾는 데만 쓴다. 이름 맞추기, 안전성 판정, 약 코드나 질병 코드로 바로 찾을 수 있는 정보에는 쓰지 않는다 |
| 대상 | 1) 허가정보 문장 998,656개 2) 생활습관 팩트표 조각 105개 |
| 단위 | 허가정보는 문장 1개(출처 번호 S, E와 같은 단위), 팩트표는 생활습관 항목 1개 등 아래 표 |
| 약을 구분하는 키 | 허가번호(item_seq). 품목기준코드(EDI) 행은 21,924개지만 허가번호는 20,714개라 같은 허가의 문장을 두 번 만들지 않는다 |
| 모델과 차원 | 개발 text-embedding-3-small(1536), 데모 text-embedding-3-large를 dimensions=1536으로 줄여서 사용 |
| 찾는 순서 | 약 코드, 질병 코드로 SQL이 먼저 좁히고, 그 안에서 벡터 Top-K(3에서 5개), 점수 기준 미만은 버림, 0건이면 no_evidence |
| 언제 만드나 | 약이 처음 쓰일 때 그 약의 문장만 만들어 저장(지연 적재). 전체 약을 미리 만들지 않는다 |

## 1. 무엇을 임베딩하나

| 대상 | 규모 | 임베딩할 글 |
|---|---|---|
| 허가정보 문장 | 허가번호 20,714개, 문장 998,656개. 약마다 평균 48.2개(중앙 51, 최대 109, 최소 1), 문장 0개인 약 없음 | "약이름 항목명: 문장" 한 줄. 머리말을 붙이는 이유는 문장만으로는 어느 약의 말인지 알 수 없기 때문 |
| 팩트표 생활습관 항목 | 질환 10개, 항목 46개 | "질환 항목명: 목표 실천 문장들" 한 줄 |
| 팩트표 목표 지표 | 질환당 1개, 10개 (지표 26개를 묶음) | "질환 목표 지표: 지표와 목표값들" |
| 팩트표 약 연결 | 35개 | 질환과 약 계열, 주의, 조언 |
| 팩트표 위험 신호 | 질환당 1개, 10개 (신호 38개를 묶음) | "질환 위험 신호: 신호들" |
| 질환 겹침 규칙 | 4개 | 조건과 규칙 |

팩트표 조각은 모두 105개(46 + 10 + 35 + 10 + 4), 글자 9,645자, 토큰 9,353개, 가장 긴 조각이 206토큰이다.

- 허가정보 전체 글은 약마다 매우 길어서, 안내문을 만들 때와 같이 고른 항목의 문장만 쓴다. 그래야 안내문과 챗봇이 같은 근거를 본다. 고른 문장의 글자 수는 허가번호 기준 5,272만 자다.
- 단위를 문장으로 한 이유는 출처 번호가 이미 문장 단위이기 때문이다. 문장은 짧아서 앞뒤 맥락이 빠지므로(문장 토큰 중앙 43, 95% 지점 133, 최대 303), Top-K를 뽑은 뒤에 같은 항목의 앞뒤 1문장을 붙여 답변 재료로 넘긴다(멘토님 말씀의 결과 후보정).
- 임베딩하지 않는 것: 용법용량과 보관 방법. 챗봇 범위가 복용법과 처방 변경을 제외하고(챗봇 문서 v0.7), 약 코드가 정해져 있으면 보관 방법은 DB에서 바로 읽는 쪽이 정확하다. 용법용량은 약마다 평균 약 10개 문단, 약 816토큰이고 표(HTML)가 섞여 있어 임베딩하면 비용과 오답 위험만 늘어난다. 보관 방법은 약마다 한 줄(평균 약 21토큰)이다. 이 결정은 수인 님 확인이 필요하다.

## 2. 어떻게 찾나

1. 질문에서 약이나 질환을 알면(내 약, 내 질환, 질문에 나온 약 이름) 코드로 SQL이 후보 문장을 먼저 좁힌다.
2. 좁힌 문장 안에서만 질문 벡터와의 유사도로 Top-K(3에서 5개)를 뽑는다. 수인 님 시험에서 주제에 맞는 근거만 넣었더니 토큰이 4,800에서 2,800으로 줄었다.
3. 점수가 기준보다 낮은 것은 버린다. 하나도 안 남으면 빈 목록을 돌려주고 챗봇은 no_evidence로 답한다.
4. 좁힐 코드가 없는 질문은 허가정보 전체(약 100만 문장)에서 찾지 않는다. 팩트표 105개 조각과 이미 만들어진 약의 문장 안에서만 찾고, 거기에도 없으면 챗봇이 "어떤 약인가요?"처럼 되묻는 것을 선택지로 둔다. 챗봇 문서 7-12 ⑥의 "못 찾거나 자유 질문이면 pgvector"와 맞추는 방법이라 수인 님 확인이 필요하다. 근거는 10/6 시험이다. 질문 12개 중 1등으로 맞힌 수가 키워드 7개, 임베딩 6개였고, 임베딩은 "가슴 통증 약" 질문에 당뇨 식사 카드를 고르기도 했다.
5. 약의 문장이 아직 없으면(지연 적재 전) 질문 안에서 그 약의 문장을 바로 만들어 쓴다. 만들기에 실패하면 빈 목록(`no_candidate`)으로 끝내고 챗봇은 no_evidence로 답한다. 잘못된 근거를 내놓는 것보다 낫다.

돌려주는 모양은 수인 님 제안(입력: 질문, 약 코드 목록, 질환, Top-K / 출력: 근거 글, 출처, 약 코드 또는 팩트표 행 번호, 점수)에 두 칸만 더한다.

| 칸 | 뜻 |
|---|---|
| `sentenceId` | 허가정보 문장 번호(S12 등). 안내문 근거와 같은 번호라 출처 문구를 그대로 만들 수 있음 |
| `reason` | 목록이 비었을 때 이유: `no_code`(좁힐 코드 없음), `no_candidate`(그 약의 문장이 아직 없음), `below_threshold`(기준 미만). 원인을 로그로 남기려는 칸 |

## 3. 크기, 속도, 비용

벡터 하나는 1536차원 x 4바이트 + 8바이트 = 6,152바이트다(pgvector 설명서의 저장 크기 식, 이 환경에서 원문을 다시 열어 보지는 못했다).

| 방식 | 벡터 수 | 벡터 저장 크기 |
|---|---|---|
| 전체 약을 미리 만들기 | 998,656 + 105 = 998,761개 | 약 6.14GB (halfvec이면 약 3.08GB) |
| 데모 17개 약 | 문장 951개(49,391자) + 팩트표 105개 | 약 5.85MB + 0.65MB |
| 사용자 한 명의 약 5개 | 평균 약 241개 | 약 1.5MB |

- HNSW 인덱스는 위 크기와 별도로 저장 공간이 더 든다. 크기는 설정에 따라 달라서 이번에는 재지 못했고, 전체를 미리 만들 경우 인덱스까지 합쳐 위 크기의 대략 2배를 잡아 두어야 한다.
- 서버는 t3.small(2GB) 한 대라 전체를 미리 만드는 방식은 맞지 않는다. 그래서 약이 처음 쓰일 때 그 약의 문장만 만들어 저장하고, 다음 사용자는 저장된 것을 쓴다. 만드는 일은 처방전 확인(OC-02) 뒤 워커에서 하므로 챗봇 응답 시간에 들어가지 않는다.
- 챗봇 응답 중에 임베딩하는 것은 질문 한 줄뿐이다. 멘토님이 지적한 "텍스트를 임베딩하면 시간이 늘어난다"는 이 한 번의 호출이고, 실제 시간은 Locust로 잴 때 같이 기록한다.
- 차원은 1536으로 고정한다. pgvector의 vector 인덱스(HNSW, IVFFlat)는 2,000차원까지라 large의 기본 3072차원은 인덱스를 만들 수 없고, dimensions=1536으로 줄이면 small과 표, 인덱스를 그대로 쓴다. 모델을 바꾸면 벡터를 새로 만들어야 하므로 저장할 때 모델 이름을 같이 남긴다.

### 토큰과 비용 (전체를 한 번 만든다고 가정한 계산, 실제 호출 아님)

| 항목 | 값 | 방법 |
|---|---|---|
| 문장 본문 | 약 5,270만 토큰 | 글자 5,272만 자 x 글자당 토큰 1.00 (표본 775,703토큰 / 775,708자) |
| 머리말 | 약 3,815만 토큰 | 문장마다 약 이름 28.2토큰(표본 300개 약 이름을 문장 수로 가중) + 항목명 약 10토큰(추정) = 38.2토큰 x 998,656 |
| 팩트표 | 9,353 토큰 | 105개 조각 |
| 합계 | 약 9,090만 토큰 | |
| text-embedding-3-large ($0.13 / 100만 토큰, OpenAI 모델 페이지) | 약 $11.8 | |
| text-embedding-3-small (약 $0.02 / 100만 토큰) | 약 $1.8 | 단가는 확인하지 못한 값이라 참고용 |

- 머리말이 문장 본문의 약 72%에 해당한다. 약 이름에서 괄호 안(성분명, 수출명)을 빼면 이름이 문장당 28.2토큰에서 15.1토큰으로 줄어 합계가 약 7,780만 토큰(large 약 $10.1)이 된다(표본 300개 계산). 다만 괄호 안 성분명은 "아목시실린" 같은 질문을 찾는 데 도움이 될 수 있어, 줄일지는 점수 기준을 잴 때 검색 품질과 같이 보고 정한다.
- 약 하나를 지연 적재할 때는 평균 약 4,400토큰이고 large 기준 $0.0006이다. 데모 17개 약은 약 8.6만 토큰, large 기준 $0.011이다.

저장 칸 제안(ERD에 넣을지는 수인 님과 정한다): `evidence_chunks(id, kind[drug_sentence, lifestyle_item, lifestyle_target, med_link, warning, cross_rule], ref_key[허가번호 또는 질환 번호], sentence_id, text, embedding vector(1536), embedding_model, created_at)`, 인덱스는 (kind, ref_key)와 embedding의 HNSW.

## 4. 점수 기준 (아직 정하지 못함)

- 점수는 코사인 유사도(1 - pgvector의 `<=>` 거리)로 쓴다.
- 기준값은 모델마다 달라서(small과 large 분포가 다름) 지금 숫자를 적지 않는다. 설정값(`.env`)으로 두고 아래 방법으로 정한다.
  1. 골든셋(제안: 챗봇 질문 10개와 근거가 없어야 하는 질문 몇 개)에서 질문마다 정답 문장을 사람이 표시한다.
  2. 기준값을 바꿔 가며 두 지표를 잰다. 정답 문장이 Top-K 안에 들어온 비율(recall@K), 근거가 없는 질문이 빈 목록으로 끝난 비율.
  3. 근거 없는 질문을 놓치지 않는(빈 목록으로 끝나는) 쪽을 먼저 지키는 기준을 고르고, 모델을 바꾸면 다시 잰다. 이 두 지표와 전후 비교는 평가 3-1(지표 2개 이상, 실험 비교) 재료가 된다.
- 재려면 OpenAI 키가 필요해서 아직 못 했다. 점수 분포를 보기 전에는 숫자를 정하지 않는다. 임베딩 설계가 확정된 뒤에 잰다.

## 5. 왜 이렇게

| 선택 | 이유 |
|---|---|
| 임베딩은 검색에만 | 임베딩은 뜻이 비슷한 글을 찾는 방법이라 정확히 같은 것을 찾는다는 보장이 없다. 안전성 판정은 DB 조회로만 하고(NFR-032), 임베딩은 후보를 찾는 데만 쓴다 |
| 이름 맞추기는 n-gram | 약 이름은 글자 모양이 틀리는 문제라 뜻을 비교하는 임베딩보다 글자 조각이 맞다(`ocr_fuzzy_match.md`) |
| 코드로 먼저 좁힘 | 10/6 시험에서 임베딩만으로는 엉뚱한 질환 카드를 골랐다. 좁힌 안에서만 찾으면 다른 약의 문장이 근거로 섞이지 않는다 |
| 점수 미만은 버림 | 근거가 없는데 가장 비슷한 문장을 억지로 내놓으면 챗봇이 근거 없는 답을 만든다. 빈 목록이 no_evidence로 이어지게 한다 |
| 답을 만든 뒤 근거 이탈 검증 | 임베딩이 찾아도 답이 근거를 벗어날 수 있어서 챗봇 쪽 7단계 검증을 그대로 둔다 |
| 용법용량, 보관은 임베딩 안 함 | 챗봇 범위 밖이거나 코드로 바로 읽을 수 있다 |

## 6. 남은 것

- 점수 기준 측정과 머리말 줄이기 품질 비교(둘 다 OpenAI 키 필요), 지연 적재가 데모 시연에서 첫 질문을 느리게 하는지 확인(데모 약은 미리 넣어 두면 됨)
- 수인 님과 정할 것: `evidence_chunks`를 ERD v1.5에 넣을지와 만드는 사람, 반환 칸 `sentenceId`와 `reason`, 좁힐 코드가 없는 질문의 처리(4번 항목), 용법용량과 보관을 임베딩하지 않는 것
- 멘토님께 물을 것: 지연 적재가 합리적인지, 문장 단위에 앞뒤 문장을 붙이는 후보정이 맞는 방향인지
