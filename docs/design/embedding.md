# 임베딩 한 장 (무엇을, 어떻게, 왜)

10/16 작성, 10/19 갱신. 10/14 회의 5번과 멘토링 4회차 "임베딩 차원 수, 임베딩할 데이터, Top-K 후 후보정"에 대한 답이다. 10/16 작성본은 설계만 있었고, 10/17부터 10/18까지 시험으로 검색과 판정 방식을 정해 2장과 4장을 고쳤다. 10/19에 같은 규칙을 서비스 코드(`app/services/rag/`)로 옮겼다(PR #107).

3장의 숫자는 두 가지 방법으로 얻었다. 개수와 글자 수는 허가정보 DB 전체(21,924행)를 안내문 근거 선택 규칙으로 전부 세었다. 토큰 수는 무작위 300개 허가번호 표본(문장 14,810개)을 cl100k 토크나이저로 세어 글자당 토큰 비율을 구한 뒤 전체에 곱했다. 3장의 비용은 실제 호출이 아니라 계산한 값이다. 4장의 검색과 판정 시험은 프로젝트 OpenAI 키로 직접 돌려 잰 값이다.

## 1. 무엇을 임베딩하나

| 대상 | 규모 | 임베딩할 글 |
|---|---|---|
| 허가정보 문장 | 허가번호 20,714개, 문장 998,656개. 약마다 평균 48.2개(중앙 51, 최대 109, 최소 1), 문장 0개인 약 없음 | "약이름 항목명: 문장" 한 줄. 머리말을 붙이는 이유는 문장만으로는 어느 약의 말인지 알 수 없기 때문 |
| 허가정보 용법용량 문단 | 허가번호 20,714개 x 약마다 평균 약 10.4개 문단 = 약 21.6만 개 (표본 300개 약의 3,130문단에서 추정, 전수 아님) | "약이름 용법용량: 문단" 한 줄. 표(HTML)는 글로 풀어서 넣음 |
| 팩트표 생활습관 항목 | 질환 10개, 항목 46개 | "질환 항목명: 목표 실천 문장들" 한 줄 |
| 팩트표 목표 지표 | 질환당 1개, 10개 (지표 26개를 묶음) | "질환 목표 지표: 지표와 목표값들" |
| 팩트표 약 연결 | 35개 | 질환과 약 계열, 주의, 조언 |
| 팩트표 위험 신호 | 질환당 1개, 10개 (신호 38개를 묶음) | "질환 위험 신호: 신호들" |
| 질환 겹침 규칙 | 4개 | 조건과 규칙 |

팩트표 조각은 모두 105개(46 + 10 + 35 + 10 + 4), 글자 9,645자, 토큰 9,353개, 가장 긴 조각이 206토큰이다.

- 허가정보 전체 글은 약마다 매우 길어서, 안내문을 만들 때와 같이 고른 항목의 문장만 쓴다. 그래야 안내문과 챗봇이 같은 근거를 본다. 고른 문장의 글자 수는 허가번호 기준 5,272만 자다.
- 단위를 문장으로 한 이유는 출처 번호가 이미 문장 단위이기 때문이다. 문장은 짧아서 앞뒤 맥락이 빠지므로(문장 토큰 중앙 43, 95% 지점 133, 최대 303), 고른 뒤에 같은 소항목의 조각을 묶어서(최대 8조각, 소항목의 첫 문장은 항상 포함) 답변 재료로 넘긴다(멘토님 말씀의 결과 후보정). 앞뒤 1문장을 붙이는 방식과 정답 글 적중이 같았고(85개와 85개), 자몽주스 질문처럼 "영향 없음" 문장과 "권장하지 않는다" 문장이 두 문장 떨어진 경우에 앞뒤 1문장으로는 뒤 문장이 빠져서 묶음을 기본으로 둔다.
- 용법용량은 임베딩한다. 챗봇 범위가 복용법(약 정보, 먹는 법)이라 "하루 몇 번 먹어요", "식후에 먹어야 하나요" 같은 질문이 들어오고(챗봇 문서 한눈에 챗봇 범위), 약 코드가 정해져 있어도 문단이 평균 10개, 약 816토큰이라 통째로 넘기기보다 질문과 가까운 문단만 고르는 편이 토큰이 적다. 대신 처방 변경이나 복용 중단 요구는 챗봇 쪽에서 먼저 걸러진다(⑥ 앞 갈래).
- 보관 방법은 임베딩하지 않는다. 약마다 한 줄(평균 약 21토큰)이라 약 코드로 DB에서 바로 읽는 쪽이 정확하다.
- 시험에서는 문장 1개를 조각 1개로 쓰지 않고 정리한 조각(v2)을 썼다. 표(HTML)는 하나로 합쳐 태그를 벗기고, 제목뿐인 조각은 없애 "큰제목 > 소항목" 경로로 붙이고, 6자 미만 조각은 뺐다. 임베딩 입력은 `약이름 구분 > 제목 > 소항목: 본문` 형태다. 시험 문서에서 조각 수가 1,340개에서 1,044개로 줄었다. 질문 175개에서 임베딩 Top-5 적중이 문장 단위 72개(61%)에서 정리 조각 82개(69%)로 올랐다(14승 4패, p=0.031). 머리말 방식은 이름 포함 82개, 없음 80개, 짧게 78개로 차이가 확인되지 않아 이름 포함을 유지했다. 이 단위로 전체를 만들면 개수가 위 숫자보다 줄어든다(전체 적재 전에 다시 센다).

## 2. 어떻게 찾나

10/17부터 10/18까지 시험으로 정한 순서다(v7). 시험 결과는 4장에 있다.

1. 질문에서 약이나 질환을 알면(내 약, 내 질환, 질문에 나온 약 이름) 코드로 SQL이 후보 글을 먼저 좁힌다. 수인 님 시험에서 주제에 맞는 근거만 넣었더니 토큰이 4,800에서 2,800으로 줄었다.
2. 약도 질환도 없는 질문은 근거 검색을 하지 않고 no_evidence로 답한다(앞단 규칙). 허가정보 전체(약 100만 문장)에서 찾지 않는 것도 같은 이유다. 10/6 시험에서 질문 12개 중 1등으로 맞힌 수가 키워드 7개, 임베딩 6개였고, 임베딩은 "가슴 통증 약" 질문에 당뇨 식사 카드를 고르기도 했다. 이 규칙의 득실은 4장에 있다. 코드가 없을 때 챗봇이 "어떤 약인가요?"처럼 되묻는 것을 쓸지는 챗봇 서버 흐름이라 수인 님과 맞춘다.
3. 질문을 LLM(gpt-4o-mini)으로 한 번 의학 용어로 다시 쓴다(예: "멍하다"를 졸음 또는 주의력 저하로). 질문이 묻는 내용은 바꾸지 않는다.
4. 좁힌 범위의 조각이 90개 이하이면 그 조각을 모두 후보로 삼는다. 넘으면 원문 질문과 재작성 질문 각각에 대해 임베딩 순위와 pg_trgm(`word_similarity`) 순위의 상위 30개씩, 모두 4가지 순위를 합쳐(중복은 한 번만) 후보로 삼는다. 원문 질문을 함께 쓰는 이유는 재작성 질문 하나만 쓰면 재작성이 틀릴 때 그대로 손해를 보기 때문이다.
5. LLM(gpt-4o-mini)이 후보 중 질문과 관련 있는 조각을 최대 8개 고른다. 고른 조각은 소항목 묶음으로 넓힌다(1절).
6. 판정 3개(A, B, C)를 모두 돌려 2개 이상이 통과하면 근거로 쓰고, 아니면 no_evidence로 답한다. A는 이 근거로 답할 수 있는지(ENOUGH, PARTIAL, INSUFFICIENT), B는 질문이 묻는 사실이 글에 직접 적혀 있는지, C는 근거만으로 답을 2문장 이내로 쓴 뒤 FULL, PARTIAL, NONE으로 가르는 판정이다. 복용 중단, 빼먹음, 두 배 복용, 수술이나 검사 전 같은 위험 주제는 2개 이상이 완전히 통과할 때만 통과시킨다. 판정은 근거 검색 함수가 맡아 통과 정도를 `coverage`로 함께 돌려주고, 부분 답변 문구는 챗봇 쪽에서 정한다(6절).
7. 약의 문장이 아직 없으면(지연 적재 전) 질문 안에서 그 약의 문장을 바로 만들어 쓴다. 만들기에 실패하면 빈 목록(`no_candidate`)으로 끝내고 챗봇은 no_evidence로 답한다. 잘못된 근거를 내놓는 것보다 낫다.

돌려주는 모양은 수인 님 제안(입력: 질문, 약 코드 목록, 질환, Top-K / 출력: 근거 글, 출처, 약 코드 또는 팩트표 행 번호, 점수)에 세 칸을 더한다. 고르는 개수는 최대 8개라 Top-K는 이 상한으로 대신한다.

| 칸 | 뜻 |
|---|---|
| `sentenceId` | 허가정보 문장 번호(S12 등). 안내문 근거와 같은 번호라 출처 문구를 그대로 만들 수 있음 |
| `reason` | 목록이 비었을 때 이유. `no_code`(약도 질환도 없음), `no_candidate`(그 약과 질환의 조각이 없음), `no_selection`(LLM이 고른 글이 없음), `insufficient`(판정 다수결을 통과하지 못함), `risk_blocked`(위험 주제인데 완전 통과가 아님), `llm_error`(OpenAI 호출 실패, 안전 쪽으로 빈 목록), `timeout`(제한 시간 초과, 안전 쪽으로 빈 목록). 챗봇은 `reason`이 있으면 no_evidence로 이어간다. 기준 미만(`below_threshold`)은 점수 기준값을 쓰지 않기로 해서 뺐다 |
| `coverage` | 근거가 얼마나 충분한지. `full`(판정 3개 중 2개 이상이 "충분" 쪽), `partial`(통과했지만 그렇지 않음), `none`(통과하지 못했거나 목록이 빔). 새 판정을 만드는 것이 아니라 이미 낸 판정 3개를 하나로 줄인 값이다. 챗봇은 이 값으로 답, 부분 답, "확인이 어렵습니다" 중에서 고른다 |

결과에는 이 밖에 다시 쓴 질문(`rewritten`), 판정 3개(`verdicts`), 단계별 걸린 시간(`seconds`)도 담긴다. `seconds`는 Locust 측정용 기록이다.

시간 제한 인자는 모두 선택이고, 넣지 않으면 기존 동작 그대로다. `timeout_sec`은 OpenAI 호출 한 번의 제한 시간, `max_attempts`는 한 호출이 다시 시도를 포함해 부르는 최대 횟수, `budget_sec`은 `search()` 전체의 제한 시간이다. 단계가 차례로 이어져서 앞의 두 값만으로는 전체 시간이 정해지지 않으므로, 챗봇 작업 제한(25초)에 맞추려면 `budget_sec`을 쓴다. 제한을 넘기면 근거 목록을 비우고 `reason`을 `timeout`으로 돌려준다. 근거를 늦게 내놓는 것보다 비우는 쪽이 안전해서다.

## 3. 크기, 속도, 비용

벡터 하나는 1536차원 x 4바이트 + 8바이트 = 6,152바이트다(pgvector 설명서의 저장 크기 식, 이 환경에서 원문을 다시 열어 보지는 못했다). 아래 개수와 크기는 문장 단위 기준이다. 정리 조각(v2)으로 만들면 개수가 줄어든다(1절).

| 방식 | 벡터 수 | 벡터 저장 크기 |
|---|---|---|
| 전체 약을 미리 만들기 | 문장 998,656 + 용법용량 약 216,000(추정) + 팩트표 105 = 약 121.5만 개 | 약 7.47GB (halfvec이면 약 3.74GB). 문장만이면 6.14GB |
| 데모 17개 약 | 문장 951개(49,391자) + 용법용량 약 177개(추정) + 팩트표 105개 | 약 5.85MB + 1.1MB(추정) + 0.65MB |
| 사용자 한 명의 약 5개 | 평균 약 293개(문장 241 + 용법용량 52) | 약 1.8MB |

- HNSW 인덱스는 위 크기와 별도로 저장 공간이 더 든다. 크기는 설정에 따라 달라서 이번에는 재지 못했고, 전체를 미리 만들 경우 인덱스까지 합쳐 위 크기의 대략 2배를 잡아 두어야 한다.
- 서버는 t3.small(2GB) 한 대라 전체를 미리 만드는 방식은 맞지 않는다. 그래서 약이 처음 쓰일 때 그 약의 문장만 만들어 저장하고, 다음 사용자는 저장된 것을 쓴다. 만드는 일은 처방전 확인(OC-02) 뒤 워커에서 하므로 챗봇 응답 시간에 들어가지 않는다.
- 챗봇 응답 중에 부르는 것은 임베딩 2회(원문과 재작성 질문)와 LLM 5회(재작성 1, 고르기 1, 판정 3)다. 판정 3개는 입력이 같아 동시에 부를 수 있지만, 재작성, 고르기, 판정은 앞 단계 결과가 있어야 해서 순서대로 걸린다. 멘토님이 지적한 "텍스트를 임베딩하면 시간이 늘어난다"에 해당하는 부분이다. 실제 OpenAI로 질문 5개를 한 번씩 돌려 잰 시간은 판정까지 간 4개가 3.7초에서 8.6초, 고른 글이 없어 일찍 끝난 1개가 1.9초였다(첫 질문 8.6초는 임베딩 3.5초와 재작성 2.1초가 커서 첫 호출 영향으로 보이나 확인하지 않았다). 표본이 5개라 평균이나 상한으로는 쓰지 않는다. Locust로 잴 때 단계별로 나눠 기록하고, 판정을 줄이는 선택지는 안전 쪽 결과가 달라지므로(4장) 같이 다시 본다.
- 차원은 1536으로 고정한다. pgvector의 vector 인덱스(HNSW, IVFFlat)는 2,000차원까지라 large의 기본 3072차원은 인덱스를 만들 수 없고, dimensions=1536으로 줄이면 small과 표, 인덱스를 그대로 쓴다. 모델을 바꾸면 벡터를 새로 만들어야 하므로 저장할 때 모델 이름을 같이 남긴다.

| 용법용량 | 약 2,470만 토큰 (추정) | 본문 약 1,690만(약마다 816토큰) + 머리말 약 780만(문단 21.6만 x 36토큰), 표본 300개 약에서 추정 |

| text-embedding-3-small (약 $0.02 / 100만 토큰) | 약 $2.3 | 단가는 확인하지 못한 값이라 참고용. 문장만이면 약 $1.8 |

- 머리말이 문장 본문의 약 72%에 해당한다. 약 이름에서 괄호 안(성분명, 수출명)을 빼면 이름이 문장당 28.2토큰에서 15.1토큰으로 줄어 문장 부분의 합계가 약 7,780만 토큰(large 약 $10.1)이 된다(표본 300개 계산, 용법용량 머리말은 별도). 다만 괄호 안 성분명은 "아목시실린" 같은 질문을 찾는 데 도움이 될 수 있다. 머리말 방식을 비교했을 때(1절) 차이가 확인되지 않아 이름 포함을 유지했고, 괄호 안을 줄일지는 전체 적재 전에 한 번 더 재서 정한다.
- 약 하나를 지연 적재할 때는 문장과 용법용량을 합쳐 평균 약 5,600토큰이고 large 기준 $0.0007이다. 데모 17개 약은 문장만 약 8.6만 토큰, large 기준 $0.011이다.

저장 칸은 `evidence_chunks`(ERD v1.5)로 구현했다. 칸: `chunk_id`(출처 번호, 챗봇이 돌려받는 `sentenceId`), `kind`(drug, fact, cross), `drug_code`, `disease_code`, `section`(E, S, P), `group_key`(같은 소항목 묶음), `seq`, `source_order`(시험에서 쓴 조각 순서), `heading`, `content`, `search_text`, `embed_text`, `drug_name`, `source_ids`, `embedding vector(1536)`, `embedding_model`, `created_at`. 처음 제안한 7가지 kind 대신 시험에서 쓴 정리 조각(v2) 모양을 그대로 따랐다. 인덱스는 `drug_code`, `disease_code`, `group_key`에 걸고, 벡터 인덱스(HNSW)는 걸지 않았다. 범위를 코드로 먼저 좁힌 안은 평균 수백 개라 정확한 전체 비교로 충분하다(3장). 서버 코드는 `app/services/rag/`, 적재는 `scripts/rag/load_evidence_chunks.py`, 마이그레이션은 `10_..._evidence_chunks.py`(vector, pg_trgm 확장 포함)다.

## 4. 근거 없음을 가리는 방법과 시험 결과

10/17부터 10/18까지 질문 세트 네 개로 잰 결과다. 정답 표시는 AI 3명 투표(3명 중 2명이 정답으로 본 글)이고 사람 확인은 아직 없다. 표는 시험 코드(`eval_v7.py`)로 다시 계산할 수 있다. 더 자세한 표와 한계는 `임베딩_4장_초안_v6_1017` 문서에 있다.

### 4.1 점수 기준값은 쓰지 않는다

점수로는 근거 없는 질문을 가를 수 없다. 설계 질문 175개(정답 글이 있는 119개, 근거 없는 56개)에서 두 집단을 구분하는 지표(AUC)가 임베딩 1위 점수 0.73, pg_trgm 0.63에서 0.67이다. 기준을 0.40으로 두면 근거 없는 질문 24/56개가 통과하고, 0.50으로 두면 답이 있는 질문 51/119개가 막힌다. 그래서 점수 기준값(`.env` 설정)과 `below_threshold`는 쓰지 않고 2장 6번의 LLM 판정으로 가린다. 판정 모델을 haiku, sonnet, opus로 바꿔도 결과가 거의 같아서 큰 모델로 바꾸는 것이 해법은 아니었다.

### 4.2 정답 글 찾기

기존 권장안은 원문과 재작성 질문 각각의 임베딩 Top-3와 pg_trgm Top-3를 합치고 소항목 묶음을 붙인 것이다. v7은 2장의 4번과 5번(후보를 넓게 모으고 LLM이 고름)이다. 175개는 설정을 고른 질문이라 결과가 낙관적이고, n2와 human2는 설계에 쓰지 않은 질문이다. 사람 질문 31개는 개선 과정에서 결과를 본 질문이다.

| 세트 | 정답 글이 있는 질문 | 기존 권장안 | v7 | v7 대 기존 | 반환 글자 수 (기존에서 v7) |
|---|---|---|---|---|---|
| 설계 175개 | 119 | 106 (89%) | 115 (97%) | 12승 3패, p=0.035 | 1,044에서 454 |
| 사람 질문 31개 | 23 | 19 (83%) | 21 (91%) | 3승 1패, p=0.63 | 1,309에서 593 |
| 새 질문 n2 119개 | 81 | 69 (85%) | 75 (93%) | 10승 4패, p=0.18 | 1,475에서 581 |
| 사람 질문 human2 56개 | 43 | 38 (88%) | 39 (91%) | 4승 3패, p=1.0 | 1,506에서 605 |

세 세트(31개, n2, human2)를 합치면 17승 8패, p=0.108이고, n2와 human2만 합치면 14승 7패, p=0.19다. 모두 확정되지 않는다. 확실히 말할 수 있는 것은 "정답 글 찾기는 비슷하거나 약간 낫고, 근거 글자 수는 절반 이하로 줄었다"까지다. 정답이 있는데 못 찾은 질문은 16개(175개 4, 사람 31개 2, n2 6, human2 4)다. 저장된 결과로 원인을 나눠 보니 후보를 모으는 단계에서 놓친 것이 1개(약 두 개짜리 질문이라 범위가 142조각으로 커서, 4개 순위 각각의 상위 30개에 정답 문장이 들지 못함), 후보에는 있었는데 LLM이 고르지 않은 것이 15개다. 16개 중 13개는 근거 부족 판정으로 막혔고(안전한 쪽의 실패, 대신 답할 수 있던 질문을 놓침) 3개는 다른 글로 통과했다. 고르기 단계 15개를 연구자가 읽고 나누면, 핵심 근거 문장을 못 고른 것이 9개(예: 종합비타민 질문에서 철분제제 병용 문장, 위장약 질문에서 알칼리제제 배합 금지 문장, 약을 끊어도 되는지 묻는 질문에서 치료 목표 문장)이고, 정답 표시가 약하거나 고른 다른 글로도 답이 될 것 같은 것이 6개다. 이 나눔은 사람이 확인한 것이 아니라 분석자의 해석이다.

### 4.3 근거 없음 판정

고정한 설정(다수결, 앞단 규칙, 위험주제 규칙)을 n2와 human2에는 결과를 보기 전에 정해 두고 한 번만 쟀다. 부분 답은 문서에 일부만 적혀 있어 일부만 답할 수 있는 질문이다.

| 세트 | 근거 없는 질문 잘못 통과 | 완전 답 가능 질문 막음 | 부분 답 질문 막음 |
|---|---|---|---|
| 설계 175개 | 0/56 | 3/73 | 15/46 |
| 사람 질문 31개 | 0/7 | 0/11 | 7/12 |
| 새 질문 n2 | 0/37 | 6/42 (14%) | 22/39 (56%) |
| 사람 질문 human2 | 0/13 | 0/17 | 20/26 (77%) |

- 안전 쪽은 네 세트에서 같다. 근거 없는 질문 113개(56 + 7 + 37 + 13)를 하나도 잘못 통과시키지 않았고, 실제 비율은 95% 신뢰구간으로 최대 약 3%까지 가능하다. 판정 A, B, C는 n2에서 단독으로는 놓치는 질문이 있었고(A는 1개, C는 4개), 2개 이상의 합의를 요구하자 n2에서는 사라졌다. 다만 다수결만으로는 사람 질문 31개의 H24와 human2의 G27, 두 개가 통과했고(113개 중 2개), 이 둘은 위험주제 규칙이 막았다. 그래서 0개라는 결과는 위험주제 규칙을 포함한 설정의 결과다.
- 약점은 부분 답이다. 지금은 막히면 "확인이 어렵습니다"로 끝난다. 정답이 있는 질문 중 근거와 함께 답이 나가는 비율은 n2에서 53/81(65%), human2에서 23/43(53%)이다. 부분 답을 내보낼지는 팀이 정할 일이다.
- 앞단 규칙은 부분 답이 가능한 질문도 막는다. n2에서 약도 질환도 없는 질문 12개 중 3개, human2에서 약 없는 질문 7개 중 2개가 그랬다. 시험 질문에 약 코드가 안 붙어서 생긴 일이고, 서비스는 처방 기록에서 약이 정해지므로 같은 비율이 나온다고 말할 수 없다.
- 위험주제 규칙은 잘못 통과를 막는 보험이다. 규칙이 막은 근거 없는 질문은 사람 질문 31개의 H24와 human2의 G27, 두 개뿐이고, 대신 n2에서 완전 답 4개와 부분 답 6개를 더 막았다. 빼면 n2는 완전 답 막음 2/42, 부분 답 막음 16/39가 된다.

### 4.4 한계

- 정답 표시가 AI 3명이고 사람 확인이 없다. 질문도 n2는 AI가 썼고, 사람 질문 87개(31개와 human2 56개)는 작성자가 1명(채연)이다.
- 설정은 175개에서 여러 조합을 보고 골랐다. n2와 human2는 이 선택에 쓰지 않았지만 고른 설정이 최선이라는 보장은 없다.
- 근거 없는 질문 비율은 세트별로 7개에서 56개라 구간이 넓다(human2 13개는 0에서 25%).
- 판정 3가지는 같은 모델에 서로 다른 프롬프트를 쓴 것이라 서로 독립이 아니다.
- n2의 후보 풀은 v7 이전 방식으로 만들어서, v7이 고른 글 중 풀에 없어 라벨이 없는 조각은 정답이 아닌 것으로 셈했다. 찾기에는 불리한 쪽의 편향이고 크기는 재지 않았다.
- 임베딩은 small로만 쟀다(large는 권한 없음). 판정과 고르기는 gpt-4o-mini로 쟀고, 서비스 모델을 바꾸면 다시 재야 한다.
- 질문마다 LLM 호출이 5회 든다(3장). 실제 OpenAI로 질문 5개를 한 번씩 돌려 잰 시간은 판정까지 간 4개가 3.7초에서 8.6초, 고른 글이 없어 일찍 끝난 1개가 1.9초였다(첫 질문 8.6초는 임베딩 3.5초와 재작성 2.1초가 커서 첫 호출 영향으로 보이나 확인하지 않았다). 표본이 5개라 평균이나 상한으로는 쓰지 않는다.

## 5. 왜 이렇게

| 선택 | 이유 |
|---|---|
| 임베딩은 검색에만 | 임베딩은 뜻이 비슷한 글을 찾는 방법이라 정확히 같은 것을 찾는다는 보장이 없다. 안전성 판정은 DB 조회로만 하고(NFR-032), 임베딩은 후보를 찾는 데만 쓴다 |
| 이름 맞추기는 n-gram | 약 이름은 글자 모양이 틀리는 문제라 뜻을 비교하는 임베딩보다 글자 조각이 맞다(`ocr_fuzzy_match.md`) |
| 코드로 먼저 좁힘 | 10/6 시험에서 임베딩만으로는 엉뚱한 질환 카드를 골랐다. 좁힌 안에서만 찾으면 다른 약의 문장이 근거로 섞이지 않는다 |
| 점수 기준값 대신 LLM 판정 | 점수로는 근거 없는 질문을 가르지 못한다(4.1). 근거가 없는데 가장 비슷한 문장을 억지로 내놓으면 챗봇이 근거 없는 답을 만들므로, "이 근거로 답할 수 있는가"를 서로 다른 질문 3가지로 LLM에 묻고 다수결로 가린다. 시험에서 근거 없는 질문 113개 중 잘못 통과는 0개였다(위험주제 규칙 포함) |
| 원문과 재작성 질문을 함께 사용 | 재작성 질문 하나만 쓰면 재작성이 틀릴 때 그대로 손해를 본다. 원문 질문을 함께 쓰면 재작성을 만든 모델이 달라도 결과가 비슷했다 |
| LLM이 후보에서 근거를 고름 | 후보를 그대로 넘기면 글이 길다. 고른 뒤에 넘기면 반환 글자 수가 절반 이하로 줄었고(n2에서 1,475자에서 581자) 찾기는 비슷하거나 나았다 |
| 답을 만든 뒤 근거 이탈 검증 | 임베딩이 찾아도 답이 근거를 벗어날 수 있어서 챗봇 쪽 7단계 검증을 그대로 둔다 |
| 벡터는 PostgreSQL의 pgvector에 둠 | 약 코드와 질환 코드로 먼저 좁히는 SQL과 벡터 검색을 같은 DB의 같은 조회에서 하려고 한다. 서버는 t3.small(2GB) 한 대라 벡터 DB를 따로 하나 더 운영하지 않는 쪽이 부담이 적고, 이미 쓰는 DB 이미지가 `pgvector/pgvector:pg16`이다(`docker-compose.yml`). 규모도 사용자 한 명의 약 5개에서 평균 약 293개 벡터(3장)라 이 크기에서는 정확한 전체 비교로 충분하고, 데모 약 17개는 약 1,200개 정도다. 다른 벡터 DB와 속도나 정확도를 비교한 시험은 하지 않았다. 멘토님 말씀(바로 벡터 DB로 넘어가지 말 것)에 따라 약 이름 맞추기는 pg_trgm 방식 글자 조각으로 하고, 벡터는 복약 안내 근거 검색(의미 검색)에만 쓴다 |
| 보관 방법은 임베딩 안 함 | 약마다 한 줄이라 약 코드로 DB에서 바로 읽는 쪽이 정확하다 (용법용량은 임베딩한다, 1절 참고) |

## 6. 남은 것

담당은 채연(RAG)이다. 챗봇 문서 v0.8이 임베딩과 벡터를 RAG 담당으로, 9번 항목이 근거 검색 함수 모양, 벡터 저장 표, 글 나누는 단위를 "RAG 담당과 정할 것"으로 두었기 때문이다.

| 할 일 | 담당 | 비고 |
|---|---|---|
| 반환 칸 `sentenceId`, `reason` | 채연 | 정함 (10/16 PR #97 리뷰에서 수인 님이 칸 이름에 찬성). `below_threshold`는 뺌(4.1). 챗봇은 `reason`이 비면 no_evidence로 이어가기만 한다 |
| 판정을 맡을 곳 | 채연 | 정함(10/19): 근거 검색 함수가 판정까지 한다. `search()`가 통과한 근거와 `coverage`(full, partial, none)를 돌려주고, 못 통과하면 빈 목록과 `reason`을 돌려준다. 부분 답변 문구는 챗봇 서버 몫이다. 약도 질환도 없는 질문은 챗봇이 먼저 거르고, `search()`도 `no_code`로 막는다 |
| 부분 답을 내보낼지 | 팀 | 챗봇이 `coverage`로 답, 부분 답, "확인이 어렵습니다" 중에서 고르기로 함(수인 님 제안, 10/19). 다만 `partial`은 판정을 통과한 경우뿐이라, 부분 답이 가능한 질문의 56%(n2)에서 77%(human2)는 통과하지 못해 no_evidence로 끝난다(4.3) |
| 근거 검색과 판정을 서비스 코드에 붙이기 | 채연 | 완료(코드와 시험 30개). 시험 코드와 같은 규칙인지는 시험 폴더의 실제 조각 데이터와 저장해 둔 임베딩으로 확인했다. 코드가 있는 질문 186개는 범위가 모두 90 이하라 후보 목록(전체)과 소항목 넓히기 결과가 시험 결과와 186개 모두 순서까지 같았다. 순위로 후보를 모으는 길(범위 90 초과)은 코드가 없어 범위가 전체 1,044개인 질문 20개로 확인했고 17개는 순서까지, 19개는 집합이 같았다(1개는 두 조각이 달랐고 원인은 확인하지 않았다). 서비스에서는 코드가 없는 질문이 앞단 규칙에서 먼저 막히므로, 코드가 있고 범위가 90을 넘는 질문(약을 여러 개 먹는 사용자)을 시험 질문 세트로 직접 비교하지는 못했다(그 길은 합성 데이터 시험으로만 확인). 실제 OpenAI를 부른 시험은 `scripts/rag/smoke_openai.py`로 질문 5개에 돌려 호출 실패가 0건이었다(통과 2개, 근거 부족으로 막힘 2개, 고른 글 없음 1개). 응답 시간은 위 5개 질문에서 3.7초에서 8.6초(일찍 끝난 1개는 1.9초)였고, 많은 질문과 동시 접속은 Locust로 단계별로 잰다(3장, `SearchResult.seconds`에 단계별 시간이 남음) |
| 코드 없는 질문 처리(되묻기 `clarify` 사용 여부) | 채연, 수인 | 앞단 규칙은 no_evidence로 답한다. 되묻기는 챗봇 서버 흐름이라 수인 님과 맞춘다 |
| 용법용량 임베딩, 보관 방법은 DB 조회 | 채연 | 2번 항목의 근거 확인은 수인 님에게 알림만 |
| `evidence_chunks` 저장 칸 | 채연 | 완료. 모델, 마이그레이션(`CREATE EXTENSION IF NOT EXISTS vector`, `pg_trgm` 포함), ERD v1.5 dbml에 넣었다. 이미 계산한 벡터를 함께 적재하므로 첫 적재에 OpenAI 호출이 필요 없다 |
| 안내문 출처 번호와 정리 조각의 대응 | 채연 | `sentenceId`가 정리 조각에서도 허가정보 문장 번호를 가리키는지 확인 |
| 못 찾은 질문 16개의 대응 | 채연 | 원인은 나눠 봤다(4.2). 후보 단계 1개는 약이 둘 이상일 때 후보를 더 넓게 모으는 방법을 시험해 볼 수 있다. 고르기 단계는 고정 설정이라 바꾸지 않았다 |
| 지연 적재가 데모 첫 질문을 느리게 하는지 | 채연 | 데모 17개 약은 미리 넣어 두면 됨 |
| 멘토님께 물을 것: 지연 적재가 합리적인지, 점수 기준 대신 LLM 판정으로 근거 없음을 가리는 방식이 맞는 방향인지, 부분 답을 막는 비율을 어떻게 볼지 | 채연 | 10/20 멘토링에서 |
