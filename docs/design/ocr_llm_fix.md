# OCR 약 이름 LLM 후보정 (멘토링 4회차 — "정규식 정규화 후 LLM 호출")

`app/services/ocr/llm_fix.py` · 연결은 `prescriptions.run_job` (읽기 직후, 저장 전). **기본 꺼짐.**

## 1단계는 규칙: 이름에 붙어 읽힌 제조사 떼기 (LLM 전에 먼저)

실제 CLOVA 결과 n4에서 약 이름에 제조사가 붙어 읽혔다 (`...(엘록시캄)제일약품(주)`, `...(나프타존)(주)한국팜비오-`, `넥실렌에스정제일약품(주)`).
이것이 "못 찾음"의 원인이라 LLM을 부르기 전에 정규식으로 떼도록 했다 (`drug_names.strip_maker` · `NameMatcher.without_maker`).

- 앞에 `)` · `-` · 공백이 있는 `○○(주)` / `(주)○○`는 규칙만으로 뗀다.
- 이름에 바로 붙은 것(`...정제일약품(주)`)은 급여목록의 제조사 이름 360종과 **정확히 일치할 때만** 뗀다 (경계를 모르는 채 자르면 이름까지 지워진다 — 처음 시도에서 점수 0.00이 되어 고침).
- 급여목록 제품명 22,045개 중 `(주)`가 들어간 이름은 0개라 진짜 이름이 지워질 위험이 없다.
- 실제 9장 전후 비교(10/14): n4 약 3줄 중 2줄이 못 찾음→찾음(넥실렌에스정 0.39→1.00, 메디아벤엘정 0.53→1.01), 엘로시드 0.50→0.73(후보 1번이 정답). 나머지 12줄과 읽지 못한 사진 5장은 변화 없음(퇴보 0).

## 2단계는 LLM: 왜 약 이름만 맡기나

10/13 실제 처방전 9장에서 LLM(gpt-4o-mini)으로 표 전체를 다시 구조화해 보니 규칙(정규식 · 표 읽기)보다 나은 점이 없었다.
읽지 못한 사진(r1 · r2 · n2 · n3)도, 못 읽은 숫자 칸(n4 1회량)도 같았다. LLM이 도울 수 있는 곳은 글자가 깨진 약 이름이라, 규칙도 "비슷한 이름 추천"(ocr_fuzzy_match.md)도 급여목록에서 못 찾은 줄만 맡긴다.

```
CLOVA → 규칙(표 읽기 · 보정 · 이름 맞추기) ─ 찾음/여럿 ──────────────→ 저장 (LLM 안 부름)
                                         └ 못 찾음 → 비슷한 이름 추천(자모 조각, ocr_fuzzy_match.md) ─ 있음 → 저장 (LLM 안 부름)
                                                    └ 그래도 못 찾음(NOT_FOUND) → [LLM: 오타 고친 이름?]
                                                                  ↓ 약 이름 글자만 보냄
                                              급여목록에서 다시 찾기 (FOUND · 점수 0.90↑) 와 원래 글자와의 유사도(0.70↑) 통과?
                                                 예 → "추천"으로 후보 1번 + 사용자가 고르는 단계(needs_confirm)
                                                 아니오 → 규칙 결과 그대로 (못 찾음)
```

## 안전장치

| 위험 | 막는 방법 |
|---|---|
| 개인정보가 외부로 나감 | 보내는 것은 약 이름 글자뿐 (환자 · 병원 · 원문 · 복용 숫자 없음). 제조사 · 줄 앞의 급여코드 꼬리 · 끝 괄호는 정리 |
| LLM이 지어낸 약 | LLM 답은 믿지 않고 급여목록에서 다시 찾아 FOUND · 점수 0.90 이상일 때만 받음 |
| 엉뚱한 약으로 바꿈 | 원래 글자와 유사도 0.70 이상이어야 함 (mg · 밀리그램 표기 차이는 무시하고 비교). 후보 힌트도 주지 않음 (힌트를 주면 라니티딘이 니자티딘으로 끌려감) |
| 사용자가 모르고 틀린 약을 확정 | 추천은 자동 확정하지 않음 → needs_confirm (후보 1번). 항목의 `match_score`는 비우고 `suggested_by="llm"`로 표시해 화면이 "추천"임을 알림 |
| OCR 글자 속 명령문 | 답을 JSON 값으로만 읽고 DB 검색에만 씀 |
| 비용 | 처방전 한 장당 1번 호출, 이름 최대 8개 (`OCR_LLM_MAX_NAMES`). 맞은 줄 · 너무 짧은 이름은 안 보냄 |
| 장애 | 꺼짐 · 키 없음 · 시간 초과(10초) · 이상한 답 → 규칙 결과 그대로. 작업이 실패하지 않음 |

## 켜는 법

`.env`에 `OCR_LLM_FIX=true` 와 `OPENAI_API_KEY=...`. 둘 중 하나라도 없으면 LLM을 부르지 않는다.

## 사실대로 적는 한계

- **실제 호출 측정 (10/14, gpt-4o-mini, 21회씩 두 번)**: 급여목록 22,045품목에서 이름 200개 × 오타 5종류(1,000건, seed=1)를 만들어, 규칙과 "비슷한 이름 추천"이 못 찾은 **166개**만 보냈다 (`eval_llm_typos.py --call`). LLM 답이 호출마다 조금 달라서 두 번의 결과를 같이 적는다.

  | 결과 | 1차 | 2차 |
  |---|---|---|
  | 정답을 추천 | 4 (2%) | 6 (4%) |
  | 틀린 약을 추천 | **0** | **0** |
  | 고쳤지만 검증에서 걸러짐 | 91 (55%) | 120 (72%) |
  | LLM이 모르겠다고 함(null) | 71 (43%) | 40 (24%) |

  **걸러진 120건(2차)을 하나씩 채점**했다 (상표 이름이 진짜와 글자 그대로 같아야 맞은 답, `recheck_llm_answers.py`): **맞은 답은 1건**(`펜넬캐쥴` → `펜넬캡슐`, 이름이 짧고 두 글자가 깨져 유사도 0.70 기준에서 걸러짐)뿐이고 119건은 상표가 틀렸다. 걸러진 이유는 "원래 글자와 너무 다름" 45건, "고친 이름이 급여목록에 없거나 여러 약과 비슷함" 64건, "바뀐 것이 없음" 10건, "점수 0.9 미만" 1건이다. 즉 검증은 틀린 답을 막았고, 맞는 답을 버린 경우는 120건 중 1건이다.

  → 안전장치는 의도대로 동작했다(틀린 약 추천 0건, 두 번 모두). 그러나 **규칙 + 비슷한 이름 추천이 이미 오타 1,000건의 83%를 후보에 올리고, LLM이 더한 것은 4~6건(0.4~0.6%p)이었다.** 남은 오타는 대부분 흐려서 두 글자가 완전히 다른 글자로 읽힌 경우(`blur2`)라서 gpt-4o-mini는 원래 한국 약 이름을 알아보지 못하고 그럴듯한 이름을 지어내는 경우가 대부분이었다.
  그래서 **기본은 계속 꺼 둔다.** 켜면 약 이름이 외부(OpenAI)로 나가는 대가에 비해 얻는 것이 거의 없다. 이 시험은 가짜 오타라서 실제 처방전 오독과 다를 수 있고, 다른 모델이나 프롬프트는 재지 않았다.
- 화면(`recognize.tsx`)은 아직 API의 `suggestedBy`를 구분해 보여 주지 않는다 (모든 후보에 같은 안내). 후보를 미리 고르지는 않는다.
- 약 이름을 외부 AI 사업자(OpenAI)에 보내므로 개인정보 처리 방침 · 동의 문구에 반영 여부를 팀이 정해야 한다. (문구 초안 · 결정 항목: `ocr_privacy_notice.md`)
- 급여목록에 없는 약(예: 라니티딘)은 LLM이 맞는 이름을 줘도 못 찾음으로 남는다.
