# 약봉투 읽기 (10/15)

앱은 "처방전과 약봉투를 찍어 주세요"라고 안내하지만, 표 읽기는 처방전의 "투약일수" 머리글만 알았다. 약봉투 샘플 p1 · r2 · p3는 머리글이 "투약량 · 횟수 · 일수"라 읽지 못하고 "다시 찍어 주세요"로 끝났다. 그래서 약봉투 표를 따로 읽는다 (`app/services/ocr/pouch.py`).

## 어떻게 읽나

- 처방전 표를 못 읽었을 때(`parse_table`이 None)만 약봉투로 다시 본다 (`pipeline.read`). 처방전 읽기 결과는 바뀌지 않는다 (저장해 둔 샘플 17장 중 처방전 표를 못 읽던 p1 · r2 · p3 · p4 · p2만 달라지고 나머지 12장은 같음).
- **글자 순서가 아니라 위치로 읽는다.** CLOVA 글자 목록 순서는 보장되지 않는다.
  1. 같은 줄에 왼쪽부터 "투약량 · 횟수 · 일수"가 있는 곳이 머리글이다. 한 줄에 모여 있지 않으면 머리글이 아니다 (영수증 띠의 "투약일수" 하나는 머리글이 아님, 0031과 같은 이유).
  2. 숫자는 세 낱말 아래 칸 위치로 1회량 · 하루 횟수 · 총 일수에 나눈다. 칸 밖의 숫자(영수증 띠의 전화번호 · 승인번호)는 읽지 않는다.
  3. 약 이름은 투약량 칸 왼쪽 글자 중 **숫자가 있는 줄 사이 칸마다 맨 위 큰 글자 줄**이다. 숫자 줄의 세로 가운데를 모아 이웃 줄과의 가운데선으로 칸(창)을 나누고, 칸마다 가장 큰 글자 높이의 0.9배 이상인 줄 중 맨 위를 이름으로 본다 (카드형 p1 · p3는 이름 아래의 "[분류]" · 성분 · 복약 안내 문장이 더 작다). 이름보다 크지 않은 줄은 칸 밖이어도 이름 높이 평균이 나머지 평균의 1.15배보다 클 때만 이름으로 더한다. 표의 끝은 마지막 칸의 끝이라 그 아래 광고 · 안내 큰 글자는 이름이 되지 않는다. 이름은 왼쪽 끝 한글에서 시작하고 "[" · "(" · "{"로 시작하지 않으며, 오른쪽에 바짝 붙은 글자(상자 겹침 허용 −0.5줄높이 ~ 간격 1.2줄높이, 높이 0.7배 이상, 세로로 절반 이상 겹침)를 이어 붙인다. "···"로 끝난 이름 뒤에는 더 잇지 않는다. 함량(`20mg`, `0.1%`)이 조각나 있어도 이어 붙는다.
  4. 카드형은 숫자가 카드 가운데에 있어서 이름 줄 사이의 가운데선으로 칸을 나눠 숫자를 이름에 붙인다.
  5. 숫자가 하나도 없는 줄이 표의 처음이나 끝에 있으면 버리고, 가운데면 남겨서 "못 읽음"으로 사용자가 채우게 한다.
- 저장은 `doc_type = pill_bag`. 약봉투에는 교부일 · 병원 · 출생연도가 없어서 **조제일만** 읽어 `issued_date`에 넣고(API 명세서 O-2: 약봉투는 조제일), 병원 · 용법 · 출생연도는 비운다. 조제일은 "조제일" · "조제일자" 라벨 바로 뒤의 날짜만 쓰고("조 제 일 자"처럼 글자가 쪼개져도 같은 줄로 묶어 읽는다. 같은 줄은 세로 가운데 차이 글자 높이 0.3배 이내), 날짜가 둘 이상 다르면 비워서 확인하게 한다. 위아래 두 라벨 사이에 낀 날짜(r2의 "조제일자:"와 "복용완료일")는 어느 쪽인지 알 수 없어 읽지 않는다. 질병분류기호도 읽지 않아 `diseaseCodes`는 빈 배열이다 (RG-05-E1).
- 영수증 띠(환자 · 약사 이름, 주소, 전화, 승인번호)는 이름 영역도 숫자 칸도 아니라서 읽지 않는다. 마스킹 규칙은 승인번호 · 사업자번호 · 주소를 가리지 않으므로 **이 띠를 저장 범위에 넣지 않는 것이 전제**다 (`ocr_mask.md`).
- 이름 끝이 "···"로 잘린 약(p1의 `슈가메트서방정5/100···`)은 약 마스터에서 한 약과만 글자가 맞아도 **자동 확정하지 않고** 후보로 올려 사용자가 고른다 (`CUT_FLAG`). 함량이 잘렸을 수 있어서다. 후보에는 다른 함량도 같이 올라온다 (p1에서 확인).

## 흔들림 시험 (합성 변형, 실제 사진 아님)

저장해 둔 p1 · r2 · p3 · p4 결과의 좌표를 일부러 바꿔 `pipeline.read` 결과가 같은지 봤다.

- 크기 0.6배 · 1.5배, 기울기 ±1 · 2 · 3 · 5 · 8도, 0.6배 + 1도: p1 · p3 · r2 모두 읽은 약 · 숫자가 같다 (p3 jit3 한 가지 변형만 7줄로 읽혀 줄 수가 달라짐 — 줄 수 불일치로 표시됨). 기울기는 `prepare`의 보정을 거친다 (보정 전에는 p1이 1~3도만 기울어도 줄이 깨졌다). 기울기 ±2 · 4도 + 흔들림 ±2px 100번씩: p1 · r2 · p4는 전부 같고 p3는 93번 같음 · 7번 표시 · 조용히 다름 0번.
- 글자 상자 꼭짓점마다 무작위로 흔들기, 샘플당 200번(약 이름 · 숫자가 같은지, 다르면 사용자에게 표시되는지 — 줄 수 불일치 · 줄 0개 · "약 이름 줄이 확실하지 않아요"):

| 흔들림 | p1 | p3 | r2 | p4 |
|---|---|---|---|---|
| ±2px | 200 · 0 · 0 | 195 · 5 · 0 | 200 · 0 · 0 | 200 · 0 · 0 |
| ±3px | 192 · 8 · 0 | 181 · 19 · 0 | 200 · 0 · 0 | 200 · 0 · 0 |
| ±4px (글자 높이의 약 1/4, 실제보다 거친 흔들림) | 161 · 39 · 0 | 157 · 43 · 0 | 195 · 5 · 0 | 200 · 0 · 0 |

(같음 · 다르지만 표시됨 · **조용히 다름**, 4종 × 3단계 × 200 = 2,400번 중 조용히 다른 것 0번. 처음 고치기 전에는 p3 ±3px에서 200번 중 6번, r2 ±4px에서 8번이 조용히 다르게 읽혔다.)

조용히 다르게 읽히던 원인과 고친 방법:
1. 성분 줄이 이름보다 커 보이는 흔들림에서 성분 줄(예: 암브록솔염산염30mg)이 이름이 됨 → **글자 크기가 아니라 구간의 맨 위 줄을 이름으로** 한다 (맨 위 줄이 구간별 가장 큰 글자 높이의 중앙값의 0.8배보다 작을 때만 큰 글자 줄로 바꾸고, 그때는 "약 이름 줄이 확실하지 않아요" 표시를 붙여 자동 확정하지 않는다).
2. 이름 바로 아래 "[분류]" 줄이 커 보여 약 줄로 한 번 더 세어지고 숫자가 그 줄로 감 → 숫자 없는 약 줄은 다른 이름 줄과 카드 간격의 0.4배 이상 떨어져 있을 때만 더한다.
3. 함량 조각("10mg" · "0.1%")이 흔들려 작아지거나 겹침이 어긋나면 이름에서 떨어져 나가 **함량이 빠진 이름**이 됨 → 숫자로 시작하는 함량 조각은 크기 · 겹침 · 간격 조건을 느슨하게 본다 (한글 안내 문장에는 적용하지 않음).
4. 투약량 칸의 숫자가 이름 뒤에 붙어 "…250mg1"이 됨 → 숫자 칸에서 읽은 낱말은 이름 글자에서 뺀다.

## 머리글 없는 목록 (p4_2016 형식, 10/15)

머리글 "투약량 · 횟수 · 일수"가 없고 "약 이름 + 숫자 3개"만 줄지어 있는 표(영수증 아래쪽 표)를 읽는다. 칸이 무엇인지 확정할 근거가 없어서 **추정한다는 확인 표시를 응답의 `notices`에 싣고, 약 줄은 이름이 정확히 맞아도 모두 사용자 확인(needs_confirm)으로 넘긴다** (`HEADERLESS_FLAG`, `Table.headerless`). 숫자가 어느 칸인지는 추정이라 화면에서 약 이름과 숫자를 함께 확인해야 하기 때문이다. 한국 약제비 계산서 · 약봉투가 "1회 투약량 · 1일 투여횟수 · 총 투약일수" 순서를 쓴다는 가정이다.

- 한두 자리 정수들을 가로 위치로 묶어 **이웃한 세 묶음**을 칸 후보로 보고, 칸 둘 이상에 숫자가 있고 왼쪽 같은 높이에 한글 이름(3자 이상)이 있는 줄이 **간격이 고르게(중앙 간격의 ±40%) 두 줄 이상** 이어질 때만 표로 본다. 표 위 · 아래의 같은 칸 숫자(영수증 윗줄의 "투약일수 2" 등)는 이 줄 범위에 들지 않아 읽지 않는다.
- 이름 없는 숫자 격자(금액표 등)는 줄이 더 많아도 표로 보지 않고, 칸이 너무 가깝거나 멀거나 줄마다 숫자가 한 칸에만 있으면 표로 보지 않는다.
- **처방전 서식 고유의 말("질병분류기호" · "의료기관 명칭" · "요양기관기호")이 있으면 머리글 없는 목록으로 읽지 않는다.** 머리글이 지워진 처방전을 약봉투로 잘못 읽는 것을 막는다. ("교부번호"는 약국 영수증도 적어서 뺐다 — p2가 "처방전 교부번호"를 적고 있다.)
- 약 줄의 안내 문장은 읽지 않는다. p4는 안내가 숫자 표와 다른 영역(왼쪽 4칸 표 "약품 · 주의사항 · 효능 · 복약안내")에 있고 글자가 낮은 해상도에서 많이 깨져 있어서다 (아래 "복약 안내").

### 이름 글자 신뢰도 (10/15)
이름이 약 마스터와 한 약으로 맞아도, CLOVA가 이름 글자를 낮은 확신으로 읽었으면(평균 < 0.5) 자동 확정하지 않고 후보로만 올린다. 근거는 실제 사진 17장: 이름이 깨져 읽힌 줄(p4 0.35 · p2 0.37~0.45)은 이미 확정이 아니었고, 확정으로 나온 줄은 모두 0.5 이상이었다 → **17장의 결과는 하나도 바뀌지 않는다** (회귀 비교로 확인). 0.5는 5개 양식의 값에서 정한 임계값이라, 실제 사진이 더 모이면 다시 본다. 합성 시험은 신뢰도를 흔들지 않아 이 규칙을 검증하지 못한다 (단위 시험으로 경계값만 확인).

## 확인 표시가 사용자에게 가는 길 (10/15 바로잡음)

읽을 때 만드는 확인 표시(`OcrRead.meta_flags` · `row_count_mismatch`)는 **저장 단계에서 버려져 사용자에게 전혀 나가지 않았다** (10/15 점검에서 발견). 앞서 "줄 수 불일치 표시와 사용자 확인이 마지막 방어선"이라고 적은 것은 이 점에서 사실과 달랐다. 이제:

- `prescriptions.notices` (JSONB, 문장 목록, 없으면 null · 마이그레이션 `8_…_prescription_notices`)에 저장하고 처방 조회(O-2) 응답에 `notices: string[]`(없으면 `[]`)로 싣는다. **명세서에 추가 제안.** 화면(OC-02)이 이 표시를 보여 주어야 의미가 있다 (아직 화면 없음).
- 담기는 것: "교부일 못 읽음" · "조제일이 서로 다르게 적혀 있음" 같은 날짜 표시, "표 머리글이 없어 칸 순서를 추정했어요", "약 줄 수가 사진과 다를 수 있어요. 빠진 약이 없는지 확인해 주세요"(`row_count_mismatch`). 출생연도 표시는 출생연도를 저장하지 않으므로 싣지 않는다.
- 약 줄의 표시 중 "약 이름이 잘려 있어요" · "약 이름 줄이 확실하지 않아요" · "약 이름 글자가 흐리게 읽혔어요"(이름 글자의 CLOVA 인식 신뢰도 평균 < 0.5, `LOW_CONF`) · 머리글 없는 목록은 약 줄을 `needs_confirm`으로 내려서 사용자가 고르게 한다 (분석 시작 전 확인 필수, REQ-033). 숫자를 못 읽었거나 범위 밖인 칸은 기존대로 `checkFields`.
- 약 줄을 하나도 못 읽은 사진(머리글만 찾음)은 빈 처방전으로 저장하지 않고 "다시 찍기"(IMAGE_QUALITY_LOW)로 처리한다 (`reason: no_rows`).

## 복약 안내 읽기 · 저장 (옵션 ①, 10/15)

`drug_guides`에는 약별 주의 문구가 없어서(`caution` 0건) 약국이 약봉투에 **인쇄한 약별 안내**를 읽어 약 줄에 저장한다 (수인님 10/15: 약 줄마다 복약 안내 칸). 읽는 방법은 `app/services/ocr/pouch_guide.py` 머리글에 있다.

- 약 카드 칸(이름 줄 바로 위 ~ 다음 이름 줄 바로 위, 마지막은 표 끝)의 글자만 읽는다. 왼쪽 열(이름 · "[분류]" · 성분)과 숫자 칸 · 오른쪽 영수증 띠는 이 범위에 들지 않는다.
- 한 줄이 여러 조각이거나 카드 맨 위 짧은 줄이면 **표시**(chip): "쪼개지 마세요", "씹지 마세요", "위장장애 주의"처럼 조각마다 하나. 나머지는 줄을 이어 **서술어 어미(세요 · 어요 · 니다 · 십시오 …)나 . ! ?에서 끊은 문장**이다. "생리과다" · "필요"처럼 명사가 요 · 다로 끝나는 것은 끝맺음으로 보지 않는다 (그렇게 끊었다가 문장이 잘리는 것을 시험에서 찾아 고쳤다). 끝맺지 못한 조각 · 두 글자 이하는 버린다.
- **글자 확실도**: 표시 · 문장마다 평균 0.8 이상, 가장 낮은 낱말 0.6 이상일 때만 저장한다. 잘못 읽힌 복약 안내가 사실처럼 보이면 안 되어서, 불확실하면 안 보여 주는 쪽이다. (p3의 "졸음이 적은 항히스타민제입니다." 평균 0.71은 저장하지 않는다.)
- 저장: `prescription_items.guidance` (JSONB, 문자열 목록, 없으면 null). 저장 직전 **`mask()`를 적용한다** (전화번호 등이 섞여 있으면 `[전화번호]`로). 마이그레이션 `7_…_item_guidance`.
- 응답: 처방 조회(O-2)의 약 줄마다 `guidance: string[]` (없으면 `[]`). **명세서에 추가 제안** — 수인님께 확인 필요. 화면에는 "사진에서 읽은 약국 안내"처럼 사진에서 읽은 글자임을 알리는 것이 안전하다 (글자 확실도가 높아도 OCR 오독이 있을 수 있다: p3 "해열, 전통 작용" 같은 읽기가 그대로 저장됨).
- 확인한 것: p1 8약 · p3 6약의 안내가 약마다 맞는 약에 붙어 읽혔다 (p1 알마겔정 2개, 슈가메트 5개, … 소론도 2개 / p3 3 · 3 · 3 · 2 · 2 · 3). 흔들려도(±1px 100번) 전부 같았고, ±2~3px에서는 표시 사이 간격(15px)이 좁게 읽혀 두 표시가 한 문자열로 합쳐지거나 문장 경계가 달라지는 일이 있었지만(p1 ±2px 100번 중 33번, p3 13번) **다른 약의 안내가 섞이거나 없는 글자가 생기는 일은 없었다**.
- 안 읽는 것: 한 줄형(r2)은 안내가 없고, p4는 안내가 표와 다른 영역에 있어 읽지 않는다 (빈 목록). 영수증 띠는 약 카드 범위가 아니라서 읽지 않는다 (`ocr_mask.md`의 전제 ① — 승인번호 · 사업자번호 · 주소는 마스킹 규칙이 가리지 않으므로 띠를 저장하면 안 된다).

## 한계 (샘플 5종 중 4종으로 만든 규칙)

- 샘플 p1 · r2 · p3 · p4 네 종류만 확인했다. 다른 약국의 양식은 배치가 달라 읽지 못하고 "다시 찍어 주세요"가 되거나, 머리글이 없는 목록으로 읽혀 칸 순서 확인 표시가 붙는다 (잘못 읽기보다 못 읽는 쪽으로 기운다).
- 이름이 두 줄로 꺾이면 줄마다 약 하나로 읽힐 수 있다. 이때 숫자 칸 수와 약 줄 수가 달라 `row_count_mismatch`가 켜진다.
- **"조용히 틀리는 경우 0"은 약봉투 샘플 4종(p1 · p3 · r2 · p4)의 합성 흔들림 2,400번에서의 결과**이고, 처방전 형식은 아래 "해상도 · 처방전 형식 점검"에서 따로 쟀다 (그전에는 재지 않았다). 실제 사진 5장 중 일부는 앞서 나온 문제(성분 줄이 이름이 되는 것 등)가 있었고 고쳤지만, 다른 양식에서 같은 종류의 문제가 생기지 않는다는 보장은 아니다. 마지막 방어선은 `notices`의 줄 수 불일치 표시와 사용자 확인이고, 이는 **화면이 `notices`를 보여 줄 때** 작동한다.
- 글자가 흐린 약봉투에서는 이름이 깨져 읽히고, 약 마스터 대조가 비슷한 이름 하나로 자동 확정할 수 있다 (p4: "씨프로바이정250일리그럼" → 씨프로바이정250밀리그램, 글자 확실도 0.35). 이 부분은 약 이름 맞추기(`matcher`)의 기준이고 약봉투 읽기에서 바꾸지 않았다 (머리글 없는 목록은 10/15부터 이 경우에도 자동 확정하지 않는다).
- 같은 약을 처방전과 약봉투로 두 번 올리면 약봉투는 병원 이름이 없어 중복 합치기(`content_key`)가 되지 않는다.
- 복약 안내 글자는 사진에서 읽은 것이라 OCR 오독이 있을 수 있다 (확실도 기준을 통과한 것만 저장). 표시 사이 간격이 흔들림으로 좁아지면 두 표시가 한 문자열로 합쳐질 수 있다 (내용은 그대로).
- 조제일은 라벨 바로 뒤의 날짜만 읽는다. 사진 안에 서로 다른 조제일이 있거나(p1) 라벨과 날짜가 위아래 줄 사이에 끼어 있으면(r2) 비워서 사용자가 입력한다.

## 10/15 전체 점검에서 고친 것 · 남은 것

고친 것
- **여러 쪽 PDF는 첫 쪽만 읽고 나머지를 말없이 버렸다.** 이제 쪽마다 처방전 하나로 읽는다 (한 쪽도 못 읽었을 때만 그 파일을 실패로 알린다 — 처방전이 아닌 쪽이 섞인 PDF는 읽힌 쪽만 쓴다). CLOVA가 여러 쪽 PDF를 `images`에 쪽마다 나눠 돌려준다는 가정이며, **실제 CLOVA 응답으로는 확인하지 못했다** (유료 호출 금지). 단위 시험은 그 모양의 가짜 결과로 확인했다.
- **서버가 다시 시작되면 OCR 작업이 "진행 중"으로 영원히 남았다** (백그라운드 작업이 서버 안에서 돌기 때문). O-5로 조회할 때 15분이 지난 queued · running 작업은 실패(`OCR_FAILED`)로 닫는다.
- 약 줄의 `timing`(용법 문구)이 마스킹 없이 저장되던 것 → `mask()`를 거친다.

남은 것 (코드로 풀지 않음)
- 업로드 횟수 제한이 없다: 한 사용자가 계속 올리면 CLOVA 호출이 그만큼 나간다. 정책(하루 몇 장)은 팀이 정할 일이다.
- 처방 숫자 범위가 둘이다: 사용자가 O-3으로 고칠 수 있는 범위(1회량 ≤ 100, 횟수 ≤ 24, 일수 ≤ 365)가 `check_fields`의 확인 기준(≤ 10 · ≤ 6 · ≤ 180)보다 넓어서, 사용자가 맞게 고친 값도 계속 "확인" 표시가 붙을 수 있다. 어느 쪽에 맞출지는 약사 검토가 필요해 정하지 않았다.
- 작업은 서버 메모리에서 돌아서, 서버가 재시작되면 그때 읽던 사진은 사라지고 다시 올려야 한다 (원본을 저장하지 않는 결정의 결과).

## 해상도 · 처방전 형식 점검 (10/15)

**해상도**: 표 읽기의 거리 기준(칸 거리 120 · 줄 오차 40 등)이 픽셀 값이라 같은 처방전도 사진 해상도에 따라 다르게 읽혔다. 샘플 좌표를 1.5배로 키우기만 해도 r4에서 하루 횟수 3이 2로 바뀌었다 (표시 없이). 휴대폰 원본은 보통 3,000px 이상인데 우리 샘플은 대부분 1,500px 이하라 이전에는 드러나지 않았다.
→ `prepare.normalize_scale`: 글자 높이의 중앙값이 16이 되도록 좌표를 먼저 맞춘다. 실제 샘플 17장의 글자 높이는 7~28이고, 16으로 맞춰도 읽은 결과는 r3의 "줄 수 불일치" 표시 하나만 달라졌다 (표 밖의 숫자 하나가 숫자 칸에 잡혀 약 줄이 3개처럼 계산된 오탐이 사라짐). **17장 모두 0.5~4배로 키우고 줄여도 결과가 같다** (이전: 17장 중 8장이 달라짐).

**처방전 형식 흔들림** (샘플당 200번, 꼭짓점마다 ±2 · 3 · 4px 무작위 이동 — 약봉투 샘플만 쟀던 시험을 처방전 형식으로 넓힘):

| 샘플 | 다른 숫자로 바뀜 (jit 2 / 3 / 4) | 이 중 사용자에게 표시 없음 (전: 표시 여부를 따지지 않은 값 → 후) |
|---|---|---|
| n4_2019 (3줄, 글자 높이 12) | 7 / 16 / 19 | 8 / 14 / 17 → **0 / 0 / 0** |
| s2 (5줄) | 0 / 1 / 9 | 0 / 1 / 9 → 0 / 1 / 5 |
| r4 (3줄) | 0 / 0 / 4 | 0 / 0 / 3 → 0 / 0 / 0 |
| fake · r5 · r3 · s1 | 0 | 0 |

원인: n4는 이름 줄(y 305 · 332)과 숫자 줄(318 · 331)의 높이가 어긋나, 숫자 한 줄이 두 약 줄의 한가운데에 놓인다. 흔들림 하나에 이웃 약의 숫자가 된다.
→ 숫자가 두 약 줄의 한가운데쯤(가까운 줄과 먼 줄의 거리 차이가 줄 간격의 30% 미만)에 있으면 두 줄 모두 `NUMS_FLAG`("숫자가 어느 약 줄의 것인지 확실하지 않아요")를 붙이고 자동 확정하지 않고 사용자가 확인한다. 실제 샘플 17장 중 이 표시가 붙는 것은 n4(2줄)와 s2(5줄)뿐이고 깨끗한 샘플(fake · r4 · r5 · r3 · s1 · n1)에는 붙지 않는다.
남은 것: s2는 흔들림 4px에서 표시 없이 바뀌는 경우가 5/200 남는다. s2는 원래 읽기도 숫자 여러 칸이 비는 샘플이고, 바뀐 결과가 오히려 더 맞는 경우도 있어 "틀림"의 기준이 불분명하다. 처방전 형식 샘플은 6장뿐이다.
