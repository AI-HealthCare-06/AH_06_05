# 형제 약 확인 — 읽힌 이름이 목록에 있어도 "글자 하나 차이의 다른 성분 약"이 있으면 사용자가 고르게 한다

`app/services/ocr/matcher.py` (`NameMatcher.decide` · `_siblings` · `_sibling_choices`) · 연결은 `pipeline.read`, 켜고 끄는 설정은 `OCR_SIBLING_CONFIRM`.

## 어떤 문제인가

규칙(이름 맞추기)은 읽힌 이름이 급여목록의 이름과 같으면 그 약으로 **자동 확정**한다. 그런데 오타가 **다른 실제 약의 이름**이 되면 글자만으로는 구별할 수 없다.

| 진짜 약 | 읽힌 이름 (글자 하나 빠짐) | 결과 |
|---|---|---|
| 로글리코엠정 (글리메피리드 + 메트포르민) | 로글리코정 (글리메피리드) | 로글리코정으로 자동 확정 → 이후 안전성 점검 · 안내문이 엉뚱한 약 기준 |

10/14 오타 시뮬레이션 1,000개 중 1건이 이렇게 틀리게 확정됐다 (`docs/design/ocr_fuzzy_match.md`의 시뮬레이션과 같은 방식, seed=1).
약 이름 14,859개(상표 기준) 중 **1,329개(8.9%)**가 성분이 다른 한 글자 차이 형제를 가진다 (예: 글리마릴정 ↔ 글리마릴엠정, 구멘틴정 ↔ 오구멘틴정, 스로펜정 ↔ 록스로펜정).

## 어떻게 막나

- 찾은 약의 상표 이름(숫자 · 괄호 앞까지)에서 **글자 하나가 더 있거나 빠진** 다른 상표가 있고, 두 상표의 **주성분코드가 겹치지 않으면** 자동 확정하지 않고 `needs_confirm`(사용자가 고름)으로 보낸다.
- 후보는 **읽은 이름의 약이 1번**, 이어서 질문 이름과 글자가 가까운 형제 순서로 **최대 5개**(`SIBLING_CHOICES`). 후보를 3개로 자르면 진짜 약이 빠지는 경우가 있어 5개로 정했다 (아래 측정).
- 주성분코드는 성분 · 함량 · 제형이 같으면 같다 (하이로손정 ↔ 하이손정은 같은 약 → 확인하지 않음). 코드를 모르는 약이 끼면 다르다고 본다 (놓치는 것보다 한 번 더 묻는 쪽이 안전).
- 항목에는 `SIBLING_FLAG`("이름이 비슷한 다른 약이 있어요")가 붙는다. 오타 보정이 아니므로 `suggested_by`는 비어 있고, `match_score`는 실제 맞춘 점수 그대로다.
- 일부러 적용하지 않는 곳: ① LLM 추천(어차피 사용자가 고르는 단계라서), ② 약 검색 API(O-4, 사용자가 이름을 직접 친 것이므로 정확히 같으면 그 약으로 확정), ③ 성분 자료가 없는 경우(`ingredients=None`).
- 끄려면 `OCR_SIBLING_CONFIRM=false`.

## 측정 (10/14)

**1. 형제 쌍 전수 시험** — 한 글자가 더 긴 형제가 있는 쌍 839개에서, 사진이 짧은 쪽 이름(목록에 실제로 있는 이름)으로 읽혔을 때 진짜(긴 쪽) 약이 후보에 있나:

| 후보 수 | 진짜 약이 후보에 있음 |
|---|---|
| 확인 없이 (이전 방식) | 0건 — 833/839를 짧은 쪽 약으로 자동 확정 |
| 3개 | 699 (83%) |
| **5개 (채택)** | **787 (94%)** |
| 8개 | 824 (98%) |

**2. 오타 시뮬레이션** (급여목록 22,045품목에서 이름 × 5종류, 규칙만):

| 시험 | 설정 | 바르게 자동 확정 | 사용자가 고름(후보에 정답) | 틀린 약으로 확정 |
|---|---|---|---|---|
| 200개 (seed=1, 1,000건) | 끔 | 267 (27%) | 32 | **1** |
| 〃 | 켬 | 247 (25%) | 53 | **0** |
| 800개 (seed=7, 4,000건) | 끔 | 1,116 (28%) | 93 | 0 |
| 〃 | 켬 | 1,040 (26%) | 169 | 0 |

→ 켜면 오타 줄의 약 2%가 "자동 확정"에서 "사용자가 고름"으로 옮겨 간다. 두 번째 표(규칙이 못 찾은 이름에 대한 추천 · LLM 대상 166개)는 켜고 끌 때 같다.

**3. 실제 CLOVA 결과 86줄**: 형제 확인으로 바뀐 줄 **2줄(2%)** — `스로펜정(이부프로펜)`(록스로펜 · 아스로펜이 형제), `자누글루엠정`(자누글루정이 형제). 둘 다 실제로 확인이 필요한 경우였다.

## 한계 (없앨 수 없는 것)

- 후보에 진짜 약이 없는 경우가 6%(5개 기준) 남는다 — 형제가 6개 이상이고 진짜 약이 글자 거리에서 뒤로 밀린 경우. 사용자가 "후보에 없음"으로 직접 검색해 고른다 (O-4).
- 글자 하나 차이가 **아닌** 다른 약(두 글자 이상 차이, 완전히 다른 이름)이 오독으로 정확히 다른 실제 이름이 되는 경우는 이 검사가 보지 않는다. 켠 상태의 시뮬레이션 5,000건에서는 0건이었지만 이론상 가능하다.
- 인식확인 화면(`recognize.tsx`)은 확인이 필요한 항목에서 **후보를 미리 골라 두지 않는다**. 사용자가 후보를 직접 눌러야 "이 약으로 확인"이 켜지고, 확인하기 전에는 분석을 시작할 수 없다. (이전에는 1번이 기본 선택이라 읽지 않고 확인을 눌러도 읽은 이름의 약이 선택됐다.) 이 규칙은 형제 확인뿐 아니라 비슷한 이름 추천 · AI 추천 항목에도 같다. 대신 확인이 필요한 항목은 누르는 횟수가 한 번 늘어난다.
- 형제 판정은 글자 하나가 더 있거나 빠진 경우만 본다. 글자 하나가 **다른 글자로 바뀐** 형제(가모사드정 ↔ 가모시드정)는 보지 않는다 — 그 모양의 오타는 시뮬레이션에서 틀린 확정이 0건이었고, 포함하면 성분이 다른 형제를 가진 상표가 8.9%에서 32.2%(14,859개 중 4,791개)로 늘어 확인할 줄이 너무 많아져서다.
- 주성분코드가 같으면 같은 약으로 본다. 코드가 같아도 제품 규격이 다를 수 있다 (같은 성분 · 함량 · 제형이면 임상적으로 같다고 보는 기준).
