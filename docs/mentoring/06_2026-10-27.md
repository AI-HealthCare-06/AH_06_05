## 3. 기능별 결과

### 3.1 OCR 사진 저장, 같은 파일, 흐림 (채연, PR #120, #122)

- 한 일
  - 같은 파일: 같은 사용자가 같은 파일(SHA-256)을 다시 올리면 OCR을 부르지 않고 지난 결과를 씁니다. 여러 쪽 PDF는 모든 쪽을 읽었을 때만 기록합니다
  - 흐림: 호출 전 선명도 검사를 빼고, 호출 뒤 기준(글자 덩어리 12 미만 또는 평균 신뢰도 0.8 미만)으로만 다시 찍기를 안내합니다. 크기 400px 미만과 같은 파일 검사는 남겼습니다
  - 사진 24시간 임시 저장: S3에 올리고 DB에는 위치만 적습니다. 서버 역할(IAM)로만 접근하고, S3 보관 규칙(1일)과 워커가 매시간 17분에 지우는 작업 두 겹으로 지웁니다
  - OCR 워커: 업로드는 사진을 S3에 올리고(응답이 최대 8초 기다림) 대기열에 넣고, arq 워커가 S3에서 읽어 기존 읽기 코드를 그대로 돌립니다. CLOVA가 모두 실패하면 20초 뒤 1번 더 합니다. 저장이 안 되거나 워커가 죽어 있으면 예전처럼 서버 안에서 처리해 사용자에게는 오류가 아닙니다
- 흐림 실험(10/22): 사진 7장(가짜 처방전 6장, 약봉투 1장) x 흐림 14종 = 98장. CLOVA가 읽은 글자에 정답 약 이름이 있는지로 채점했습니다

| 기준 | 결과 |
|---|---|
| 호출 전 선명도 100 미만 | 약을 하나도 못 읽은 48장 중 17장만 걸렀음. 막은 24장 중 4장은 약을 모두 읽을 수 있었음 |
| 호출 뒤 기준(위) | 약을 하나도 못 읽은 48장을 모두 걸렀고 심한 흐림 42장은 모두 다시 찍기. 다시 찍기 62장 중 59장은 실제로 약을 다 못 읽은 사진 |
| 통과한 36장 | 11장은 약 일부를 못 찾음(중간 정도 흐림). 이름 확인 단계(`needs_confirm`)에 맡김 |

  신뢰도를 0.9로 올리면 11장을 모두 잡지만 읽을 수 있는 사진 7장도 막혀서 0.8을 유지했습니다. 한계는 사진 7장, 프로그램으로 만든 흐림, 이름만 채점(용량, 횟수, 일수는 안 봄)이고, 진짜 폰 흔들림은 시험하지 않았습니다.

### 3.2 근거 검색 RAG: 임베딩과 청킹 다시 정리 (채연, 10/23)

"왜 임베딩인지"부터 코드와 데이터로 다시 따졌습니다.

| 질문 | 정리 |
|---|---|
| 왜 임베딩인가 | 꼭 필요하다는 증거는 못 찾았습니다. 비용이 작고(검색 전체 중앙 4.1초 중 질문 임베딩은 중앙 0.24초, 조각 1,044개 저장은 약 6MB) 외부 근거와 맞아서 유지합니다 |
| 언제 일하나 | 약 코드와 질환 코드로 SQL이 범위를 먼저 좁히고, 범위가 90조각을 넘을 때만 임베딩과 글자 조각 순위로 후보를 모읍니다. 17개 약과 10개 질환의 모든 조합을 세면 약이 1개이고 질환이 없으면 0%, 약이 2개이면 83%에서 99%, 3개 이상이면 100%가 90을 넘습니다 |
| 우리 데이터 | 약 5개 상황 모의(질문 217개)에서 임베딩을 빼고 후보 수를 같게 맞추면 후보 단계는 임베딩 쪽이 낫지만(17 대 5, p=0.017) 최종 적중은 같습니다(136개 대 135개, 18 대 17) |
| 외부 근거 | 의료 질의응답에서 BM25 70.05, MedCPT 70.06, 합치면 71.57(MIRAGE). 한국어 일반 검색에서 BM25 37.1, 임베딩 66.5에서 69.9(MIRACL). 임베딩과 글자 검색을 합치는 구조가 일관되게 안정적입니다 |
| 청킹 | 허가정보의 문장과 항목 단위(중앙 52자)로 자르고 앞에 "약이름 구분 > 소항목"을 붙입니다. 머리말이 있는 쪽이 후보에 정답을 더 담았습니다(124개 대 110개). 의미 청킹은 쓰지 않습니다 |
| 사용자 입력 | 자르지 않고 재작성 질문과 원문을 통째로 임베딩합니다. 시험 질문 381개가 중앙 27자, 최대 81자입니다 |
| 점수 기준 | 쓰지 않습니다. 정답이 있는 질문과 없는 질문을 가르는 힘(AUC)이 0.54에서 0.67이었습니다 |

## 4. 현재 막힌 문제와 멘토님께 받고 싶은 피드백

각 항목에 "여기까지 시도했고 여기서 막혔다"와 여쭙고 싶은 점을 함께 적었습니다.

1. **[이미지 저장]** 사진을 24시간만 보관하는 방식
   - 판단 근거: 비동기 재시도와 워커 읽기가 되려면 사진을 저장해야 해서 24시간 임시 저장(S3)으로 정했습니다. 서버에서 저장과 읽기는 확인했고 삭제는 10/27 18:17 이후 확인합니다. 동의한 사진을 오래 모아 시험용으로 쓰는 안(C안)은 뒤로 미뤘습니다
   - 확인하고 싶은 점: 사용자 사진은 24시간 뒤 지우는 방향이 괜찮은지, 사진을 더 오래 모아야 한다면 동의와 보관을 최소한 어디까지 갖춰야 하는지

2. **[임베딩 유지]** 검색에 임베딩을 계속 쓰는 방식
   - 판단 근거: 후보 수를 같게 맞춰 비교하니 최종 결과는 거의 같았습니다(136 vs 135). 후보 단계에서만 차이가 났습니다(17 vs 5, p=0.017). 비용은 작습니다(전체 4.1초 중 0.24초, 저장 약 6MB)
   - 확인하고 싶은 점: 최종 차이가 거의 없는데도 임베딩을 유지하는 것이 괜찮은지, 단순화하는 편이 나은지

3. **[챗봇 근거 놓침]** 자료에 있는 문장이 답에 쓰이지 않는 문제
   - 판단 근거: "약 먹는 동안 운동해도 되나요?"에서 아토르스타의 근육병증, 횡문근융해 문장 6개가 서버 DB에 있는데 답은 "특별한 주의사항이 없다"고 했습니다(3.3). 근거 없는 질문을 잘못 통과시키는 것은 0개로 막았지만, 근거가 있는데 쓰지 못하는 쪽은 5회차에 말씀드린 부분 답 막힘(56%와 77%)과 같은 종류의 문제인지 구분이 필요합니다
   - 확인하고 싶은 점: 근거가 있는데 답에 빠지는 정도를 어떻게 재면 좋은지, 줄이려면 고르기 단계를 먼저 손봐야 하는지 답 만들기 지시를 손봐야 하는지

4. **[출력 가드레일]** 위험한 말을 놓치는 것보다 맞는 말을 막는 쪽을 택함
   - 판단 근거: "약을 안 먹어도 되는지는 의료진과 상담하세요" 같은 안전한 상담 안내도 막히고, 이걸 풀려고 하면 "네, 괜찮아요" 같은 짧은 답으로 위험한 말이 새는 길이 생겨 보류했습니다(#129 리뷰 제안 5, #116)
   - 확인하고 싶은 점: 의료 챗봇에서 정상 답을 얼마나 막아도 되는지, 실무에서는 이 균형을 어떤 기준으로 정하는지

5. **[개인정보 고지]** OpenAI로 가는 정보
   - 판단 근거: 챗봇은 건강 정보 동의가 있을 때 나이, 질환(처방전과 내 정보), 먹는 약, 질문, 최근 대화 4번을 답을 만들 때 OpenAI로 보냅니다. 흡연, 음주, 임신, 키, 몸무게, 예정 검사는 보내지 않습니다. 팀 개인정보 고지 문서(`docs/design/ocr_privacy_notice.md`)에는 아직 "보내지 않음"으로 남아 있어 코드에 맞게 고칠 예정입니다. Jev를 1층에 넣으면 질문이 또 외부로 나가서, 켜기 전에 처리 위탁과 국외 이전 고지를 정해야 합니다(#130)
   - 확인하고 싶은 점: 이런 프로젝트에서 고지와 동의를 어디까지 갖춰야 하는지, 실무에서는 어떻게 하는지

6. **[남은 기간]** 11/4 제출까지 우선순위
   - 판단 근거: 기능과 서버는 돌아가고, 남은 일은 챗봇 답 품질(3.3의 문제 3가지, 가드레일 놓침 29/77), 개인정보 문구와 앱 안내문 갱신, 플로우차트, 발표 준비입니다
   - 확인하고 싶은 점: 남은 일주일에 무엇을 먼저 하면 좋을지, 발표와 데모에서 어디에 시간을 써야 평가에 도움이 되는지
