**Figma와 달라지는 것**
- **챗봇 여는 방식: 하단 탭 대신 플로팅 버튼** — 오른쪽 아래 [AI 챗봇] 버튼을 누르면 지금 화면 위에 챗봇 창이 열림. 휴대폰은 거의 전체 화면, 넓은 화면은 오른쪽 아래 창. 닫아도 대화 유지 (4-1 항목)
- 음성 입력: 앱이 마이크를 쓰지 않고 **휴대폰 키보드의 음성 입력**을 안내 → CB-05 계열 4개 화면 불필요 (4-10 항목)
- 답변 읽어주기 🔊 추가 (고령 사용자, 4-11 항목)
- 긴급 안내: 누를 것은 **최대 3개**(119 · 가까운 응급실 · 지금은 증상이 없어요 — 과다 복용이면 칩 없음, 자해 표현과 동시 해당이면 칩 대신 109), 응급실은 **카카오맵 검색** (4-6 항목)
- 첨부 사진: **처방전 · 약봉투 → 분석 화면으로 안내**, **약 사진 → 이름 읽고 확인 후 답변** (4-9 항목)

**핵심 규칙**
- 대화 나누기: 플로팅 버튼으로 열면 **오늘 시작한 대화를 이어 감**, 분석 결과에서 들어오면 새 대화(같은 날 · 같은 대상이면 이어 감). 대화는 **첫 질문 때** 만듦 (3-5 항목)
- 긴급 · 자해 표현은 **앱에서 먼저 감지**해 서버 응답 없이도 카드를 띄움. 원문은 저장하지 않음. **둘 다 해당하면 119 · 109를 함께** 보여 주고, 자해 표현이 나오면 **24시간 동안 모든 대화에서 안전 모드** (4-6 항목)
- 실패한 질문은 사라지지 않음 — 기기에 잠시 저장하고 [다시 시도] (4-7 항목)

## 3. 데이터 · API

### 3-1. 답변 유형

| answerType | 라벨 | 화면 | 라벨 색 (톤앤매너) |
|---|---|---|---|
| `normal` | (없음) | CB-01 정상 답변 + 출처 | — |
| `clarify` | 정보 확인 | CB-01-E3 재질문 칩 | info (#1D4ED8 / #EFF6FF) |
| `partial` | 일부만 확인됐어요 | CB-01-E3 부분 근거 | neutral (#475569 / #F1F5F9) |
| `no_evidence` | 확인이 어렵습니다 | CB-01 근거 없음 | neutral |
| `refer` | 의료진 상담 필요 | CB-01 일반 정보 + 상담 안내 | warning (#B45309 / #FFFBEB) |
| `emergency` | 긴급 안내 | CB-01-E4 | danger (#DC2626 / #FEF2F2) · 빨간 테두리 |
| `crisis` | 도움 연결 | CB-01-E5 | info (#1D4ED8 / #EFF6FF) — Figma 보라색은 톤앤매너에 없어 기존 색으로 (8 항목) |
| `error` | 연결 오류 | CB-01-E6 (프론트 전용) | neutral |

API v1.2 · ERD v1.2의 `answered` / `refused_medical` / `no_evidence` → 위 이름으로 바꾸도록 요청 (8 항목).

### 3-2. 사용하는 API

| API | 용도 | 현재 명세 | 프론트 제안 |
|---|---|---|---|
| H-1 `POST /chat/sessions` | 대화 시작 | `{ analysisId?, context? }` → `{ sessionId }` | 요청에 `clientRequestId` 추가 (다시 시도 때 대화 중복 생성 방지, 7-7 항목) · E2 첫 답변을 응답에 함께: `{ sessionId, firstMessage? }` |
| H-2 `GET /chat/sessions/{id}/messages` | 이전 대화 | 형식 없음 | `{ items: Message[] }` — Message 형식은 3-3 항목 |
| H-3 `POST /chat/sessions/{id}/messages` | 질문 보내기 | `{ content }` → `{ messageId, answerType, sources }` | 아래 요청 · 응답 확장 |
| R-4 `GET /analyses/{id}` | E2 맥락 카드 | 형준 담당 | 분석일 · 약 개수 · 경고 건수 · 경고/약 이름을 여기서 꺼냄 |
| `POST /chat/messages/{id}/feedback` | 답변 피드백 | 추가 필요 (선택) | 지금은 UI만, 전송 없음 |
| H-4 `GET /chat/sessions?month=2026-09` | CB-02 기록 있는 날짜 | ⚪ 선택 구현 | `{ dates: ["2026-09-02", …], retentionFrom: "2026-04-02" }` — 보관 시작일을 함께 |
| H-4 `GET /chat/sessions?date=2026-09-16` | CB-03 그날 대화 목록 | ⚪ 선택 구현 | `{ items: [{ sessionId, title, preview, createdAt, updatedAt }] }` — 명세에 `createdAt` 추가. 날짜 · 카드 시각은 **대화를 시작한 시각** 기준 (3-5 항목) |
| H-5 `PATCH /chat/sessions/{id}` | CB-03 제목 수정 | ⚪ 선택 구현 | `{ title }` (명세 그대로, 최대 30자 제안) |
| `DELETE /chat/sessions/{id}` | CB-03 대화 삭제 | **없음** (정책 ⑩ 필수) | `204`. API 명세에 추가 요청 |
| `GET /chat/sessions/today` | 들어올 때 이어 갈 오늘 대화 찾기 | 없음 | **찾기만 하고 만들지 않음** (대화는 첫 질문 때 만들기 때문, 3-5 항목). 파라미터 없으면 오늘 시작한 마지막 대화, `?analysisId=&contextType=&contextId=`를 주면 같은 날 · 같은 분석 · 같은 대상 대화 → `TodayResponse` (`sessionId` · `hasHistory` · `safetyModeUntil`) — `hasHistory`는 지난 대화가 하나라도 있는지 (E1 문구, 4-2 항목), `safetyModeUntil`은 안전 모드가 끝나는 시각 (4-6 항목) |
| `POST /chat/sessions/{id}/attachments` | CB-04 사진 · 파일 올리기 | 없음 (REQ-079 "API 미정") | `multipart/form-data` → `{ attachmentId }`. H-3 요청의 `attachmentIds`로 넘김. 서버가 사진 종류를 판별하고 약 이름을 읽음 (4-9 항목) |
| `POST /chat/sessions/{id}/safety-events` | 앱에서 감지한 E4 · E5 기록 | 없음 | `{ ...SafetyInfo, clientRequestId }` (동시 해당이면 `types`에 둘 다) — 질문 원문은 보내지 않음 (4-6 항목). 대화가 아직 없으면(첫 질문이 응급 문장) H-1로 먼저 만든 뒤 기록. 실패하면 기기에 뒀다가 같은 `clientRequestId`로 다시 보냄 (중복 방지) |

### 3-3. 메시지 형식 · H-3 요청 · 응답 (제안)

```ts
type AnswerType = "normal" | "clarify" | "partial" | "no_evidence" | "refer" | "emergency" | "crisis" | "error";  // error는 프론트 전용

// 챗봇 창을 열 때 넘기는 값 — openChat(params) (4-1 항목). from은 기록 · 분석용이고 창 모양은 바꾸지 않음
type ChatParams = {
  from: "fab" | "CM-03" | "RG-02" | "RG-03" | "RG-04" | "CB-03";  // fab: 플로팅 버튼. CM-03: 값이 없거나 initialQuestion이 있으면 플로팅 버튼과 같음, analysisId만 있으면 분석 연계
  analysisId?: number;
  context?: { type: "warning" | "drug"; id: number };
  initialQuestion?: string;                     // from = "CM-03" 예시 질문 카드
  sessionId?: number;                           // from = "CB-03" (지난 대화 열기)
};

// R-4에서 맥락 카드에 쓰는 값만 꺼냄 (R-4 전체 형식은 형준 담당)
type AnalysisSummary = {
  analysisId: number;
  analyzedAt: string;                           // "9월 23일 분석 · 5일 전" 계산용
  drugCount: number;
  warningCount: number;
  targetLabel?: string;                         // context가 있을 때 "엔티심바정20밀리그램 + 클라리신정" · "노바스크정5밀리그람"
};

// H-1 대화 시작 응답 (3-2 항목 제안)
type StartResponse = { sessionId: number; firstMessage?: Message };   // firstMessage: context가 있을 때 E2 첫 답변

// 오늘 대화 찾기 응답 (GET /chat/sessions/today, 3-2 항목)
type TodayResponse = { sessionId: number | null; hasHistory: boolean; safetyModeUntil: string | null };  // hasHistory: 지난 대화가 하나라도 있는지 (E1 문구) · safetyModeUntil: 안전 모드가 끝나는 시각 (없으면 null, 4-6 항목)

// 대화 하나
type Session = {
  sessionId: number;
  title: string;
  createdAt: string;                            // 대화를 시작한 시각 — "오늘 대화" · 달력 날짜 기준 (3-5 항목)
  updatedAt: string;
  analysisId?: number;
  context?: { type: "warning" | "drug"; id: number };
};

// 대화 한 줄 (H-2 목록 · 화면 표시 공통)
type Message = {
  id: number;
  role: "user" | "assistant";
  content: string;
  status?: "generating" | "done";               // assistant만. 화면을 나갔다 와도 아직 만드는 중인지 알 수 있게 (4-3 항목)
  answerType?: AnswerType;                      // assistant만
  sources?: { title: string; basedOn?: string }[];
  createdAt: string;                            // ISO 8601, +09:00
  // 다시 들어왔을 때(H-2) 칩 · 카드를 그대로 다시 그리기 위한 값
  clarify?: Clarify;                            // E3 재질문 칩 (아래 응답과 같은 형식)
  suggestions?: string[];                       // E2 후속 질문
  attachments?: { type: "image" | "file"; name: string; previewUrl: string | null }[];  // CB-04. H-2에서는 서버가 보관 중이면 미리보기 주소, 보관하지 않으면 null → "사진 1장" 표시만 (9 항목 보관 기준)
  action?: { type: "open_analysis" };           // 응답과 같음 — 다시 들어왔을 때 버튼을 다시 그림
  imageResult?: "prescription" | "drug" | "unreadable";  // 응답과 같음
  safetyEvent?: SafetyInfo;                     // 앱에서 감지한 E4 · E5 (원문 없이 카드만 다시 그림, 4-6 항목)
};

// 화면 전용 상태 (서버에 저장하지 않음)
type LocalStatus = "sending" | "streaming" | "failed" | "done";
// 서버에 가지 못한 메시지(보내는 중 · 실패)는 서버 번호(id)가 없으므로 clientRequestId를 임시 번호로 씀
// "failed"인 사용자 질문은 기기에 임시 저장 → 창을 닫았다 열거나 앱을 다시 켜도 E6 카드와 함께 다시 보임. 다시 보내기에 성공하면 지움 (4-7 항목)

// 요청
type SendRequest = {
  content: string;                              // 사용자가 보낸 글자 (칩을 고른 경우 "노바스크정 · 종합감기약")
  clientRequestId: string;                      // 다시 시도 때 중복 저장 방지 (E6)
  clarifyAnswers?: Record<string, string>;      // E3 칩 선택 결과 { drug: "노바스크정", coldMedicine: "종합감기약" }
  attachmentIds?: string[];                     // CB-04로 올린 사진 · 파일 (4-9 항목)
  emergencyDismissed?: boolean;                 // E4 [지금은 증상이 없어요] 후 같은 질문을 다시 보낼 때. 서버도 응급 검사만 건너뜀 (자해 검사는 유지)
  replyTo?: number;                             // 서버가 감지한 E4에서 재개할 때 — 이미 저장된 질문 번호. 질문을 새로 저장하지 않고 그 질문에 일반 답을 새로 닮 (4-6 항목)
};

// 응답
type SendResponse = {
  messageId: number;
  answerType: AnswerType;                       // 3-1 항목
  content: string;
  sources: { title: string; basedOn?: string }[];   // basedOn: "2026-09 기준" (정책 ⑥)
  clarify?: Clarify;                            // answerType = clarify 일 때
  suggestions?: string[];                       // 이어서 물어볼 질문 (E2)
  action?: { type: "open_analysis" };           // 처방전 · 약봉투 사진 → 답변 아래 [처방전 · 약봉투 분석하러 가기] 버튼 (4-9 항목)
  imageResult?: "prescription" | "drug" | "unreadable";  // 사진에 대한 판별 결과 — 사진 안내(처방전 · 읽지 못함)를 일반 답변과 구분 (피드백 여부 등, 4-3 · 4-9 항목)
  safety?: SafetyInfo;                          // 서버 2차 감지 결과 — answerType이 emergency · crisis일 때. 동시 해당 · 과다 복용 여부를 함께 알림 (4-6 항목)
};

// 오류 (3-6 항목 표로 화면 처리를 정함)
type ChatError = { kind: "network" | "timeout" | "http"; status?: number; code?: string };

// 긴급 · 자해 감지 결과 (앱 1차 · 서버 2차 공통, 4-6 · 7-2 항목)
type SafetyInfo = {
  types: ("emergency" | "crisis")[];            // 동시 해당이면 둘 다
  overdose: boolean;                            // 과다 복용 · 잘못 복용 규칙에 걸렸는지 — true면 [지금은 증상이 없어요] 칩을 보여 주지 않음
  rule: string;                                 // 걸린 규칙 이름 (원문은 담지 않음)
};

type Clarify = {
  items: { key: string; question: string; options: string[]; allowInput: boolean }[];  // 최대 2개 항목
};
```

- 위 타입 중 API v1.2에 **없는 것은 모두 백엔드와 협의할 제안** — `firstMessage` · `hasHistory` · `status` · `clarify` · `suggestions` · `action` · `imageResult` · `attachments` · `safetyEvent` · `clientRequestId` · `clarifyAnswers` · `attachmentIds` · `emergencyDismissed` · `replyTo` · `safety` · `safetyModeUntil` (8 항목)
- 보내는 중인 메시지의 첨부는 기기 안 주소로 미리보기를 보여 주고, 서버에서 다시 불러온 뒤에는 `previewUrl`을 씀
- 글자가 차례로 나오는 방식(SSE)은 미정. 지금은 mock에서 한 번에 받은 답을 화면에서 차례로 보여 주기만 한다. 받는 부분은 교체 가능하게 둔다 (7-1 항목).

                                 ※ 홈의 세 진입 모두 from: "CM-03" — 넘기는 값이 없거나 initialQuestion이 있으면 플로팅 버튼과 같음, analysisId만 있으면 분석 연계
플로팅 버튼 [AI 챗봇]            → { }  (일반 질문 모드)
※ 모든 진입은 화면 이동 없이 openChat(params) — 밑의 화면(홈 · 분석 결과)은 그대로 남음

### 3-5. 대화 나누는 규칙

"새 대화" 버튼 없이 들어오는 방법으로 대화를 나눈다 (REQ-077 · ERD `chat_sessions` 메모 "날짜별 여러 대화" 방향).

| 들어오는 방법 | 동작 |
|---|---|
| 플로팅 버튼 [AI 챗봇] | **오늘 시작한** 마지막 대화를 이어 감 — 분석 결과에서 시작한 대화도 포함 (들어가면 방금 하던 대화가 있는 게 고령 사용자에게 가장 쉬움, 맥락 카드로 무엇에 대한 대화인지 보임). 오늘 시작한 대화가 없으면 빈 새 대화 화면 (E1 화면 · 4-2 항목) |
| 홈 예시 질문 카드 (`initialQuestion`) | 플로팅 버튼과 같게 오늘 대화를 이어 가고, 그 질문을 바로 보냄 (오늘 대화가 없으면 이 질문으로 새 대화) |
| 날짜가 바뀐 뒤 플로팅 버튼 | 새 대화 |
| 창을 닫았다가 **같은 날** 플로팅 버튼으로 다시 열기 | **닫기 전 모습 그대로** — 보던 대화(분석 결과 대화 · CB-03에서 연 지난 대화 포함) · 창 안 화면(달력 · 목록) · 적던 글자 · 고른 사진 · 스크롤 위치 유지. 대화는 다시 불러옴 (4-1 항목) |
| RG-03 · RG-04 · RG-02 · CM-03 (분석 결과 연계) | 새 대화 (질문 대상이 다르므로). 단, **같은 날 · 같은 분석 · 같은 대상**(경고 · 약, 또는 분석 요약)으로 이미 만든 대화가 있으면 그 대화를 이어 감 — 같은 버튼을 여러 번 눌러 대화가 쌓이지 않게 |
| CB-03에서 지난 대화 카드 | 그 대화를 열고 이어서 질문 가능 |

- 대화(세션)는 **첫 질문을 보낼 때** 만든다 (H-1). 들어오기만 하고 질문 없이 나가면 대화가 생기지 않음 → 달력에 빈 대화가 "기록 있음"으로 찍히지 않게
  - 예외: **첫 답변이 있는 진입**(`context`가 있는 RG-03 · RG-04)만 들어올 때 만든다. `analysisId`만 있는 진입(RG-02 · CM-03)은 첫 답변이 없으므로 첫 질문 때 만든다 (4-4 항목)
  - 첫 질문 전송은 **H-1(대화 만들기) → H-3(질문)** 두 단계. 사진이 있으면 **H-1 → 사진 올리기(`attachments`) → H-3** 세 단계 (사진 올리기에 대화 번호가 필요하므로). 어느 단계에서 실패해도 E6를 보여 주고, [다시 시도]는 **실패한 단계부터** 이어서 함 (앞 단계가 성공했으면 건너뜀). 모든 단계에 같은 `clientRequestId`로 중복 생성 방지
  - 이미 있는 대화에 사진을 보낼 때는 사진 올리기 → H-3 두 단계
- "오늘"은 한국 시간(+09:00) 자정 기준
- **"오늘 대화"는 오늘 시작한 대화**. CB-03에서 지난 대화(예: 9/16)를 열어 오늘 이어서 질문해도 그 대화는 9/16 대화로 남고, 플로팅 버튼의 이어 가기 대상(오늘 대화)이 되지 않음. 단, 창을 닫았다 같은 날 다시 열면 닫기 전 모습대로 그 대화가 보임
- **달력(CB-02)은 대화를 시작한 날짜에 표시**. 지난 대화를 이어 가도 원래 날짜에 남고 오늘 날짜에 새로 찍히지 않음
- 지난 대화를 이어 갈 때 그 대화가 분석 결과와 연결돼 있으면 맥락 카드를 그대로 보여 줌. 분석이 오래됐으면 정책 ⑧ 대상 (후순위)
- 대화 제목은 서버가 자동 생성 (명세 H-5 · ERD `title`). mock은 첫 질문 앞 20자

### 3-6. 오류 코드별 처리

|---|---|

| 오늘 대화 찾기 실패 (네트워크 · 500 · 503) | 빈 새 대화 화면(E1)으로 열고 상단에 "지난 대화를 불러오지 못했어요 [다시 불러오기]" 한 줄. 안전 모드는 기기에 저장된 값으로 판단 (4-6 항목). 기록 여부(`hasHistory`)를 모르므로 E1 카드 제목은 어느 경우에도 맞는 "오늘은 어떤 게 궁금하세요?" (4-2 항목). 질문은 보낼 수 있음 — 보내면 새 대화로 시작 |
| `404 NOT_FOUND` (대화 · 분석이 없거나 지워짐) | 대화: 빈 새 대화 화면(E1) / 분석: 맥락 카드 불러오기 실패와 같게 (4-4 항목) |

- 닫기 전 모습은 **앱이 켜져 있는 동안 메모리에만** 둠 (적던 글자에 건강정보가 있을 수 있어 기기에 저장하지 않음). 앱을 다시 켜거나 웹 페이지를 새로 고치면 3-5 항목 처음 규칙(오늘 대화)대로 엶. 로그아웃하면 비움
- **다시 열 때**: 같은 날이면 닫기 전 모습 그대로, 날짜가 바뀌었으면 3-5 항목 규칙대로 오늘 대화를 찾음. 어느 경우든 열 때마다 오늘 대화 찾기(안전 모드 확인)와 대화 다시 불러오기(H-2)를 함 — 창이 닫힌 사이 CB-03 삭제 등으로 바뀌었을 수 있으므로
- **창이 열린 채 다른 진입이 오면** (넓은 화면에서 창을 연 채 분석 결과의 [이 경고 챗봇에 물어보기]를 누름): 창 안 대화를 3-5 항목 규칙대로 바꿈. 적던 글자가 있으면 그대로 둠
- 열기 · 닫기 움직임: 아래에서 올라오며 나타남 200ms 정도. 기기의 "동작 줄이기"가 켜져 있으면 움직임 없이 바로 (React Native 기본 `AccessibilityInfo`)
- 휴대폰 전체 화면 창이 열려 있을 때는 **뒤 화면을 스크린 리더가 읽지 않게** 막음 (iOS `accessibilityViewIsModal` · 안드로이드 `importantForAccessibility="no-hide-descendants"` — React Native 기본). 넓은 화면의 떠 있는 창은 뒤 화면도 쓸 수 있으므로 막지 않음
- 초점: 열면 스크린 리더 초점을 창 제목으로 (휴대폰에서 입력칸에 바로 초점을 주면 키보드가 올라와 대화를 가림. 웹 넓은 화면만 입력칸에 초점), 닫으면 플로팅 버튼으로 되돌림
- 긴급 카드(E4 · E5)는 넓은 화면의 작은 창에서도 **[119 전화하기]까지 첫 화면에 보이게** — 카드가 대화 영역보다 길면 카드 위쪽에 맞춰 스크롤 (카드 안 순서가 문구 → [119 전화하기]이므로 119 버튼이 먼저 보임). 창 크기는 바꾸지 않음
- 구현: 창은 React Native 기본 `View`를 앱 루트 위에 겹쳐 둠 (`Modal`은 넓은 화면에서 밑의 화면을 누를 수 없게 막으므로 쓰지 않음). 창 안의 팝업(첨부 바텀시트 · 제목 수정 · 삭제 확인 · 피드백 이유)도 **창 안에 겹쳐** 그림 — 넓은 화면에서 페이지 전체를 덮지 않게.
- **다른 화면과 겹칠 때**: 다른 팀원 화면의 `Modal`(OCR 확인 팝업 등)은 루트 위 창보다 위에 뜨므로, 팝업을 띄우는 동안 플로팅 버튼을 숨길 수 있게 `useChatLauncher()`에 `setLauncherVisible(false)`를 둠 (채널톡 `hideChannelButton`과 같은 역할). 창이 열리고 닫힐 때 알려 주는 `onOpenChange`도 둠 (채널톡 `onShowMessenger` · `onHideMessenger`) — 예: RG-04 안내문 음성을 재생 중이면 창을 열 때 멈춤 안드로이드 뒤로 버튼은 기본 `BackHandler`, 창 크기는 `useWindowDimensions`, 안전 영역은 Expo 기본 `react-native-safe-area-context` — 새 라이브러리 없음
- **입력창 폭**: 입력칸은 남는 폭에 맞춰 줄어들고 `＋` · 🎤/전송은 고정 폭 — 폭 320에서도 전송 버튼이 창 밖으로 밀리지 않게 (4-8 항목)

**창 안 공통**

- **창이 열릴 때마다 다시 불러옴** (위) — 다른 화면에서 대화가 바뀌었을 수 있으므로
- (선택) 마지막 메시지와 시간 차이가 크면(예: 3시간 이상) 대화 사이에 "오후 7:12" 같은 시각 구분선 — 아침 대화가 저녁까지 이어질 때 덜 헷갈리게
- 대화 나누기(3-5 항목)는 `from`이 아니라 넘겨받은 값으로 정함 — `initialQuestion`이면 플로팅 버튼과 같고, `analysisId`가 있으면 분석 연계
- 새 답변이 오면 맨 아래로 자동 스크롤 — **새 답변 카드가 버튼까지 끝까지 보이게** (프로토타입에서 E4 카드가 아래로 잘린 채 멈춤, 10 항목). 사용자가 위로 올려 보고 있으면 스크롤하지 않고 [새 답변 ↓] 버튼만 표시.
- **대화가 열리는 위치**: 어느 경로로 열든 **맨 아래**(최신 메시지)에서 연다 (같은 날 다시 열면 닫기 전 스크롤 위치). 분석 결과에서 들어오면 새 맥락 카드가 보이는 위치 (프로토타입은 늘 맨 위에서 열려 오래된 대화부터 보임, 10 항목)
- **지난 차례의 버튼 · 칩은 비활성화**: E2 후속 질문 · E3 재질문 칩 · E4 [지금은 증상이 없어요]는 **가장 최근 답변에 붙은 것만** 누를 수 있음. 한 번 누르거나 다음 메시지가 오가면 흐리게 · 누를 수 없게 (프로토타입은 오래된 칩이 계속 눌려 중복 전송됨, 10 항목)
  - **예외: 화면 이동 버튼** (사진 안내의 [처방전 · 약봉투 분석하러 가기] · E4 [119 전화하기] · [가까운 응급실 찾기] · E5 전화 버튼) — 다시 눌러도 중복 전송 같은 문제가 없으므로 계속 누를 수 있음
  - **예외: E6 [다시 시도]** — 다른 질문을 먼저 보내도 계속 누를 수 있음. 실패한 질문을 다시 보낼 방법이 없어지면 안 됨 ("보낸 질문은 그대로 남아 있어요"). 성공하면 버튼은 사라지고, 답변 위치는 4-7 항목 규칙을 따름 (마지막 메시지면 제자리, 아니면 맨 아래에 질문 인용과 함께)
- 누를 수 없는 버튼은 모양으로도 구분 (흐린 색). 입력이 비어 있을 때 전송 버튼이 활성 모양이면 고장으로 보임

**고령 사용자 · 접근성**

- **기기 글자 크기**: 휴대폰 글자 크기를 가장 크게 해도 말풍선 · 칩 · 입력창 · 버튼이 잘리거나 겹치지 않게. 고정 높이 대신 내용에 맞춰 늘어나게 하고, 칩은 줄바꿈. 개발용 진입 화면에서 큰 글자로 확인
- **화면 읽기(스크린 리더)**: 아이콘만 있는 버튼에 이름을 붙임 — `＋` "첨부" · 🎤 "음성 입력 안내" · ↑ "보내기" · 🔊 "답변 듣기" / ⏹ "듣기 멈춤" · 달력 "대화 기록" · `<` "뒤로" · 플로팅 버튼 "AI 챗봇 열기" · × "챗봇 닫기". 라벨(의료진 상담 필요 등)은 본문 앞에 함께 읽히게
- **키보드 · 화면 가장자리**: 키보드가 올라오면 입력창이 키보드 바로 위로 올라오고, 마지막 메시지도 가려지지 않게. 아이폰 하단 · 노치 영역(안전 영역) 안쪽에 배치
- **누르는 영역**: 칩 · 피드백 · 글자 버튼 포함 모든 누를 수 있는 요소 48 이상 (보이는 크기가 작아도 누르는 영역은 넓게)

### 4-2. CB-01-E1 첫 대화

- 오늘 대화가 없을 때 표시 (빈 새 대화 화면). 첫 질문을 보내면 대화가 만들어지고 CB-01로 이어짐
- 분석 연계로 들어온 경우(RG · CM-03 `analysisId`)에는 E1 대신 맥락 카드 · 후속 질문 칩을 보여 줌 (4-4 항목)
- 제목 "무엇이든 물어보세요" · 설명 "복용 중인 약과 생활습관에 대해 답해 드려요"
- 카드 제목은 기록 여부에 따라 다르게
  - 대화 기록이 전혀 없음 (`hasHistory: false`, 3-2 항목): "아직 나눈 대화가 없어요" (Figma)
  - 지난 기록은 있음: "오늘은 어떤 게 궁금하세요?" (신규 · 임시) — 지난 대화는 상단 달력 아이콘으로
  - 오늘 대화 찾기가 실패해 기록 여부를 모를 때: "오늘은 어떤 게 궁금하세요?" (3-6 항목)
- "이런 질문으로 시작해 보세요" + 추천 질문 3개 → 누르면 그 글자로 바로 전송
- 공통 고지를 카드 아래에 표시
- 추천 질문 문구는 임시 예시 (REQ-076 "팀 확인 필요")

### 4-3. CB-01 대화

- 사용자 말풍선: 오른쪽 · 파랑
- 답변 말풍선: 왼쪽 · 흰 카드. 위에서부터 [라벨] → 본문 → 출처 → 🔊 · 피드백
- 출처: "출처 · 식약처 의약품 허가정보 〉" → 누르면 펼쳐서 출처명 · 기준일 · 공통 고지
- 답변 생성 중: "● ● ● 답변을 만들고 있어요" → 글자가 차례로 나옴. 생성 중에는 전송 버튼을 막음 (추가 전송 방지)
- 답변을 만드는 중에 창을 닫거나 앱을 나가도 **서버는 답변을 끝까지 만들어 저장**하고, 다시 열면 H-2로 완성된 답을 불러옴 (고령 사용자는 기다리다 나가기 쉬움). H-2에서 `status: "generating"`이면 "● ● ●"를 이어서 표시하고 **2초마다** 다시 불러옴. 60초가 지나도 완성되지 않으면 E6 (임시 값, 3-3 항목). 서버와 협의 필요 (8 항목). mock은 답변을 계속 만들어 둠
- 피드백: [도움 됐어요] [답변이 이상해요] → "이상해요"는 이유 선택 (사실과 달라요 · 질문과 달라요 · 기타). 지금은 앱 안에서만 표시 상태 유지
  - 누르면 **선택된 모양으로 바로 바뀜** (프로토타입은 눌러도 반응 없음)
  - **고른 뒤에도 바꿀 수 있음** (고령 사용자는 잘못 누르기 쉬움 · 좋아요 👍👎와 같은 익숙한 방식)
    - 같은 버튼을 다시 누르면 취소 (아무것도 안 고른 상태) · 반대쪽을 누르면 바뀜
    - "이상해요" → 이유 선택 창. 이유를 **안 골라도** 닫을 수 있고 "이상해요"는 기록됨. 고르면 함께 저장
    - "이상해요"에서 "도움 됐어요"로 바꾸면 골랐던 이유는 지움
    - 고른 직후 버튼 옆에 "알려 주셔서 고마워요"를 2초 정도 작게 표시
    - 서버는 마지막 선택만 저장 (덮어쓰기). 취소를 지원하려면 피드백 API가 "선택 없음" 값도 받아야 함 (8 항목) — 지금은 화면에서만 처리하므로 **창을 다시 열거나 앱을 다시 켜면 선택이 사라짐** (대화를 다시 불러오므로) (피드백 API가 생기면 H-2에 선택 값 포함 필요)
  - 붙이는 곳: 실제 답변(`normal` · `partial` · `no_evidence` · `refer`, E2 첫 답변 포함)에만. `clarify` 재질문 · E4 · E5 · E6 · 안내 문구("다행이에요 …" 등) · **사진 안내**(`imageResult`가 `prescription` · `unreadable`인 답변)에는 붙이지 않음. 사진 속 약을 확인한 뒤의 약 설명은 실제 답변이므로 붙임
- refer 답변은 서버가 보낸 문구를 그대로 표시 (문구 3종은 정책 ⑦)

### 4-4. CB-01-E2 분석 결과를 알고 시작하는 대화

- 맥락 카드는 넘겨받은 값에 따라 두 가지
  - `context`가 있을 때 (RG-03 · RG-04): "분석 결과를 알고 있어요" / "9월 23일 분석 · 5일 전 · 약 6개 · 경고 3건" / "질문 중인 경고 · ○○ + ○○" (약이면 "질문 중인 약 · ○○")
  - `analysisId`만 있을 때 (RG-02 · CM-03): 위 카드에서 "질문 중인 …" 줄만 빼고 분석 요약만. 첫 답변 없이 후속 질문 칩만 — 이 진입은 대화를 첫 질문 때 만들어 서버 추천을 받을 시점이 없으므로 **앱에 둔 고정 칩**(`copy.ts`) 사용 (6 항목)
  - 프로토타입은 `analysisId`만 있을 때 맥락 카드가 전혀 없음 (10 항목)
  - 첫 설명(H-1)을 받지 못하면: E6가 아니라 맥락 카드 아래에 "설명을 불러오지 못했어요 [다시 불러오기]" — 사용자가 보낸 질문이 없으므로 "보낸 질문은 그대로 남아 있어요"(E6)와 맞지 않음. [다시 불러오기]는 같은 `clientRequestId`로 H-1을 다시 부름
  - 분석 결과(R-4)를 불러오지 못하면: 맥락 카드 자리에 "분석 결과를 불러오지 못했어요 [다시 불러오기]" 한 줄만 보여 주고 대화는 그대로 가능 (첫 답변은 H-1 응답으로 따로 받으므로 영향 없음)
- 첫 답변 (`context`가 있을 때): 넘겨받은 경고 · 약 **설명** + 출처. "○○에 대해 물어보세요" 같은 안내 문장만으로 끝내지 않음
  - 경고: 무엇이 왜 위험한지 + "처방한 의사나 약사에게 꼭 알려 주세요"
  - 약: 무엇에 쓰는 약인지 · 어떻게 먹는지 한두 문장 (RG-04 내용과 같게)
- "이어서 물어볼 수 있어요" + 후속 질문 칩 (서버 `suggestions`). 약 중단 · 변경 질문은 칩으로 두지 않음
  - 경고 예: "근육 이상은 어떤 증상으로 나타나나요?" / "의사 · 약사에게 어떻게 말하면 되나요?" (Figma)
  - 약 예: "먹는 걸 잊으면 어떻게 하나요?" / "같이 먹으면 안 되는 음식이 있나요?" (임시 · 근거 자료 범위 안에서 확정 필요, 정책 ⑥)
- 대화가 길어지면 맥락 카드를 위에 고정할지 접을지는 미정 → 우선 **첫 메시지 위에 두고 스크롤과 함께 올라가게**
- 오래된 분석 판단 · 재분석 안내(정책 ⑧)는 후순위

- clarify 답변: [정보 확인] + "정확한 안내를 위해 두 가지만 확인할게요." + 항목별 칩 (최대 2개 항목)
  - 항목 예: ① 지금 드시는 약 — [노바스크정 (분석한 내 약)] [다른 약 직접 입력] / ② 감기약 종류 — [종합감기약] [해열진통제] [기침약] [잘 모르겠어요]
  - 분석 결과가 있으면 첫 칩에 내 약 목록, 없으면 직접 입력만
  - [다른 약 직접 입력] · "직접 입력" 항목은 누르면 입력창에 포커스 + 입력칸 안내 글자 "약 이름을 입력해 주세요". 글자만 써 두고 입력할 곳이 없으면 안 됨 (프로토타입, 10 항목)
  - 칩은 **말풍선 안**에 둠 (Figma). 항목마다 칩을 고르면 **그 항목만 선택 표시** (전송 전에는 다시 골라 바꿀 수 있음). **모든 항목이 채워져 전송된 뒤에** 그 말풍선의 칩을 모두 비활성화 (같은 칩을 다시 눌러 중복 전송되지 않게)
  - **항목을 채우는 방법**: 칩 선택 · [잘 모르겠어요] · 직접 입력 중 하나
  - **직접 입력은 [직접 입력] 칩을 누른 경우에만** — 입력창이 "항목 입력 중" 상태로 바뀌고 입력창 위에 "① 지금 드시는 약 입력 중 · 취소"를 표시. 이 상태에서 적고 보내면 그 항목이 채워짐 (아직 서버로 보내지 않음). [취소]를 누르면 보통 입력창으로
  - **모든 항목이 채워지면 자동으로 한 번에 전송** — 선택 결과를 사용자 말풍선으로 보내고 (`노바스크정 · 종합감기약`, 요청의 `clarifyAnswers`) 같은 화면에서 답변이 이어짐
  - 칩을 누르지 않고 입력창에 적어 보내면 **새 질문** — 재질문은 버리고 새 질문으로 처리
- partial 답변: [일부만 확인됐어요] + "자료에서 확인된 내용은 여기까지예요. …" + 확인되지 않은 부분 + 출처

### 4-6. CB-01-E4 긴급 안내 · CB-01-E5 도움 연결

**감지 · 기록 (E4 · E5 공통)**

- **앱에서 먼저 검사**: 전송 직전 입력 글자를 1차 키워드 규칙으로 확인 (사진을 함께 보내면 글자만 검사, 사진만 보내면 검사하지 않음) → 걸리면 서버 응답을 기다리지 않고 바로 카드 표시 (오류 · 네트워크 끊김 중에도 빠지지 않게)
- 서버도 같은 규칙을 2차로 적용해 `emergency` · `crisis`를 내려줄 수 있음 → 같은 카드로 표시
- **E4 · E5에 동시에 걸리면** (예: "사라지고 싶어서 약을 한꺼번에 먹었어요") — 지금 119가 필요하면서 109 상담도 필요한 상황이므로 한쪽만 보여 주지 않음
  - **E4 카드(119 먼저)를 보여 주고, 카드 바로 아래에 E5 안내를 함께** 붙임. 이때 E5 안내는 **[109 전화하기]와 고정 문구만** — [지금 위험하다면 119]는 바로 위 E4 카드에 있으므로 빼서 같은 버튼이 두 번 나오지 않게
  - 이 경우 **[지금은 증상이 없어요] 칩을 보여 주지 않음** (아래 "칩을 보여 주지 않는 경우")
  - 회의용 프로토타입은 E4를 먼저 검사하고 끝나서 109 안내가 빠짐 (10 항목)
- **글자와 사진을 함께 보냈는데 글자가 걸리면**: 사진도 올리지 않고 원문과 함께 앱 메모리에만 둠. [지금은 증상이 없어요]로 재개할 때 함께 보냄 (4-9 항목)

**안전 모드 (E5 · 동시 해당 뒤)**

- 자해 · 자살 표현(`crisis`)이 한 번 나오면 **그때부터 24시간 동안, 그 사용자의 모든 대화에서 안전 모드** — "괜찮다"는 말이나 질문 맥락이 바뀐 뒤에 안전장치가 풀리는 것을 막음 (챗봇 안전 연구에서 확인된 문제, 11 항목)
  - **대화 단위가 아닌 사용자 단위**인 이유: 대화 단위면 분석 결과에서 새 대화로 들어오거나(3-5 항목) 다음 날 새 대화가 되면 안전 모드가 풀려, 같은 우회가 대화를 바꾸는 방식으로 생김
  - 24시간은 임시 값 — 전문가 검토 (9 항목)
  - 24시간 안에 자해 표현이 다시 나오면 그때부터 다시 24시간
  - 대화는 끊지 않음. 일반 복약 질문("혈압약은 아침에 먹나요?")에는 답함 (Figma E5 "대화를 강제로 끝내지 않음")
  - 약의 양 · 한꺼번에 먹기 · 위험한 양에 관한 질문은 계속 E5로 보냄 (수치를 답하지 않음, 7-2 항목). 처방대로 먹으려는 질문("이 약 한 번에 몇 알 먹어요?")도 여기에 걸리므로, 이때는 E5 안내 아래에 "먹는 양은 약봉투나 처방전에 적힌 대로 드시고, 궁금하면 약사에게 물어봐 주세요."를 붙임 — 수치는 알려 주지 않고 방법만 안내
  - 입력창 바로 위에 **"힘들 때 109 · 24시간"** 한 줄을 작게 고정 — 누르면 `tel:109` (웹은 번호 글자도 함께). 사람의 도움이 늘 보이게. **닫을 수 없음** (안전 목적), 대신 입력창을 가리지 않는 작은 크기(Caption 14)
- **판단 방법**: 챗봇이 열릴 때 오늘 대화 찾기 응답의 `safetyModeUntil`(3-2 · 3-3 항목)이 지금보다 뒤면 안전 모드. 대화 중 `crisis`가 새로 나오면 앱에서 바로 켜고 **"지금 + 24시간"을 기기에도 바로 저장** (7-6 항목, 서버도 같은 시각을 기록)
  - **어느 경로로 들어오든** 챗봇이 열릴 때 오늘 대화 찾기를 부름 — CB-03에서 지난 대화를 여는 경우(`sessionId`가 있음)도 안전 모드 · `hasHistory` 확인용으로 부름 (그 대화는 받은 `sessionId`로 엶)
  - 화면을 열어 둔 채 끝나는 시각이 지나면 다음 질문을 보낼 때 앱이 확인해 끔 ("힘들 때 109" 안내도 그때 사라짐)
  - **찾기가 실패하면 켜진 쪽으로** — 기기에 저장해 둔 마지막 `safetyModeUntil`로 판단 (7-6 항목). 안전 기능은 확인하지 못할 때 꺼진 채로 열리면 안 됨
- **대화를 지워도 안전 모드는 유지** — 안전 모드 판단용 기록(시각 · 종류만, 원문 없음)은 24시간 동안 서버에 남김. 대화 삭제(CB-03)나 전체 삭제(MY-S1)로 풀리지 않음 (개인정보 · 전문가 검토, 9 항목)
  - **단, 탈퇴 · 민감정보 동의 철회 때는 즉시 지움** — 정책 ⑨ "탈퇴 시 즉시 파기", 안건 #6 파기 범위("동의 철회 = 챗봇 대화 삭제")와 맞춤. 대화 삭제는 "이 대화를 안 보고 싶다"지만, 탈퇴 · 철회는 "내 건강정보를 쓰지 말라"는 뜻이므로 안전 모드 기록도 남기지 않음
- 앱에서 걸린 경우 **질문 원문은 서버로 보내지 않고**, "긴급 안내(또는 도움 연결)를 보여 줬음" 표시만 저장 (시각 · 걸린 규칙 이름 · `emergency` / `crisis`) — 정책 ③ "대화 원문은 남기지 않음"과 맞추고, 다시 들어왔을 때(H-2) 카드가 사라지지 않게. 저장용 API 필요 (3-2 · 8 항목)
  - 원문은 E4 [지금은 증상이 없어요]에 쓰려고 **앱 메모리에만** 잠시 들고 있음. 사용자가 이 칩을 눌러 "증상이 없다"고 확인한 경우에만 그때 원문을 일반 질문으로 보냄 (이때부터 저장됨)
  - **기록 저장이 실패하면** (네트워크 끊김 · 첫 질문이라 H-1 실패 등): 카드는 그대로 보여 주고, 기록(원문 없음)을 기기에 뒀다가 **다음 요청 때 같은 `clientRequestId`로 다시 보냄** (다시 들어올 때 · 다음 질문을 보낼 때). 성공하면 기기에서 지움. 기록이 빠지면 다시 들어왔을 때 카드가 사라지고 안전 모드도 서버에 남지 않기 때문
  - 다시 들어오면 사용자 말풍선 자리에 원문 대신 "(이전에 긴급 안내를 보여 드린 질문이에요)"를 흐리게 표시하고 카드를 그대로 보여 줌. 원문이 없으므로 복원된 카드의 [지금은 증상이 없어요]는 **비활성화**
- 웹에서는 `tel:` 링크가 전화를 걸 수 없는 경우가 있어 번호를 글자로도 함께 보여 줌

**E4 · 카드 구성**

- 빨간 테두리 · [긴급 안내] · 고정 문구 · [119 전화하기] (`tel:119`, 빨강 채움) · [가까운 응급실 찾기] (지도 앱, 빨강 테두리만) · 답변 중단 고지 · [지금은 증상이 없어요] (카드 안, 회색 테두리 — 과다 복용 · 동시 해당에는 없음)
  - 카드에서 누를 것은 **최대 세 가지** (과다 복용 · 동시 해당이면 칩이 빠지고, 동시 해당이면 아래 E5 안내에 [109 전화하기] 하나가 붙음) — 응급 상황에서는 선택지가 적을수록 빨리 결정함. "가까운 응급실 찾기"와 이름이 비슷한 응급의료포털 링크는 카드에 두지 않음 (아래)
  - 버튼 순서는 **[119 전화하기]가 먼저**. 응급 상황에서는 119가 병원을 정해 주므로 응급실 찾기는 보조 수단
  - 두 버튼을 같은 모양으로 두지 않음 — 119가 먼저라는 게 한눈에 보이게 (프로토타입은 둘 다 빨강 채움, 10 항목)

**E4 · 가까운 응급실**

- [가까운 응급실 찾기] → **카카오맵 "응급실" 검색** `kakaomap://search?q=응급실`. 카카오맵 앱이 없으면 모바일 웹 `m.map.kakao.com/scheme/search?q=응급실`로 엶 (카카오맵 공식 URL 스킴 문서). `q`는 URL 인코딩해서 보냄. 위치는 지도 앱이 처리하므로 **우리 앱은 위치 권한이 필요 없음** (음성 입력을 키보드에 맡긴 것과 같은 원리)
  - 구현: 설치 여부를 미리 확인(`canOpenURL`)하지 않고 **앱 주소로 열기를 시도 → 실패하면 웹 주소로** 엶. iOS의 `canOpenURL`은 `app.json`에 스킴 등록이 필요하고 Expo Go에서는 제대로 동작하지 않을 수 있기 때문. 웹 플랫폼에서는 처음부터 웹 주소
  - 카카오맵을 고른 이유: 앱이 없을 때 웹으로 대신 열 수 있어 어떤 기기에서든 열림. 네이버 지도(`nmap://search`)는 앱이 있어야 하고 웹 대체 방법이 문서에 없음
  - 한계: "응급실" 검색에는 응급실이 없는 병원도 섞일 수 있고 실시간 병상 정보가 없음 → 아래 응급의료포털 링크로 보완
  - 확인 필요 (9 항목): 좌표(`p`)를 빼면 현재 위치 기준으로 검색되는지 · 문서의 웹 주소는 `http://`인데 `https://`로도 열리는지
- **응급의료포털 링크는 [가까운 응급실 찾기]를 누른 뒤에만** — 지도 앱에서 돌아오면 카드 아래에 "응급실만 따로 보려면: 응급의료포털 ›"을 보여 줌 (지도 결과가 부정확하다고 느낀 사람에게만 필요)
  - 돌아온 순간 알아내기: 앱은 React Native 기본 `AppState`가 다시 "활성"(`active`)이 될 때, 웹은 탭이 다시 보일 때(`visibilitychange`). 지도 앱 · 웹을 **열지 못했으면 바로** 포털 링크를 보여 줌
- "응급의료포털 ›" → 응급의료포털 E-Gen 응급실 찾기 `https://www.e-gen.or.kr/egen/search_emergency_room.do` (보건복지부 · 국립중앙응급의료센터, 응급실만 · 등급 · 반경 · 거리순). 좌표 없이 열어 위치 권한이 필요 없음. 실시간 병상 정보는 이 페이지에서 확인하지 못해 문구에 "병상"을 넣지 않음

**E4 · [지금은 증상이 없어요]**

- 이 칩은 "예전에 가슴이 아팠어요" 같은 **과거형 · 가정형 문장이 잘못 걸렸을 때** 풀어 주는 용도
- **칩을 보여 주지 않는 경우** — 119 안내만 남김
  - **과다 복용 · 잘못 복용 규칙에 걸렸을 때** (`SafetyInfo.overdose: true`) — 약을 많이 먹은 경우 지금 증상이 없어도 안전하다고 볼 수 없음 (증상이 늦게 나타나는 약도 있음)
  - **E4 · E5 동시 해당일 때** — 몸의 위험과 자해 위험이 겹침
- [지금은 증상이 없어요] → "다행이에요. 다시 증상이 생기면 바로 119에 연락해 주세요. 복약에 관한 질문은 계속 하실 수 있어요." 표시 + 같은 질문으로 일반 답변 재개 (정책 ③)
  - **사용자 말풍선을 새로 만들지 않음** — 질문은 이미 화면에 있으므로, 답만 그 질문 아래(긴급 카드 다음)에 이어서 붙임
  - 앱에서 감지한 경우 (원문이 서버에 없음): 원문을 새 요청(새 `clientRequestId`)으로 처음 보냄 + `emergencyDismissed: true`
  - 서버가 감지한 경우 (원문이 이미 서버에 저장됨): 같은 `clientRequestId`로 보내면 서버가 중복으로 보고 예전 긴급 답을 돌려주고, 새 ID로 보내면 질문이 두 번 저장됨 → **`replyTo`(질문 번호)와 `emergencyDismissed: true`를 함께 보내** "이 질문에 일반 답을 새로 달아 달라"고 요청 (3-3 · 8 항목)
- `emergencyDismissed: true`로 다시 보낼 때는 **그 질문에 한해 앱의 1차 응급(`emergency`) 검사를 건너뜀** — 같은 질문이 다시 걸려 E4가 반복되는 것을 막음. 자해 · 자살(`crisis`) 검사는 건너뛰지 않음
- 서버가 2차로 감지해 내려준 E4에서 누른 경우도 같음 — 서버도 `emergencyDismissed`이면 응급 검사만 건너뛰고 자해 검사는 유지 (8 항목)
- 건너뛰는 건 그 한 번뿐. 다음 질문부터는 다시 검사

**E5 · 카드 구성**

- 차분한 색 · [도움 연결] · 고정 문구 · [109 전화하기] (`tel:109`, 파랑 채움 · 기본) · [지금 위험하다면 119] (테두리만 · 보조) · 복약 질문 재개 안내. 대화를 강제로 끝내지 않음
- E4와 동시 해당이면 E4 카드 아래 붙는 형태로 [109 전화하기] · 고정 문구만 (위 "감지 · 기록")
- 이후 24시간 안전 모드 (사용자 단위, 위)

### 4-7. CB-01-E6 답변 오류

- 3-6 항목 표에서 E6로 가는 오류(네트워크 · 시간 초과 · 500 · 503 · 429, H-1 · 사진 올리기 · H-3 어느 단계든) → 사용자 질문은 그대로 두고 [연결 오류] 카드 + [다시 시도]
- 다시 시도는 같은 `clientRequestId`로 재전송. 다시 실패하면 같은 화면 유지
- 오류 뒤에 다른 질문을 먼저 보내도 [다시 시도]는 계속 누를 수 있음 (4-1 항목 예외)
- 다시 시도에 성공하면 — 화면 순서와 서버 기록 순서(다시 들어왔을 때 H-2)가 같게
  - 실패한 질문이 **마지막 메시지**면: 오류 카드를 **그 자리에서 답변으로 바꿈** (프로토타입은 맨 아래에 "다시 보냈어요"가 따로 붙고 오류 카드가 그대로 남음, 10 항목)
  - 뒤에 **다른 대화가 이어졌으면**: 답변은 **맨 아래**에 붙이고 위에 "↩ 아까 보낸 질문: ○○"를 인용해 보여 줌. 오류 카드는 "다시 보냈어요 ↓"로 바뀜 (서버는 다시 보낸 시각으로 저장하므로, 제자리에 넣으면 다시 들어왔을 때 순서가 달라짐)
- 실패한 질문은 **기기에 임시 저장** → 창을 닫았다 열거나 앱을 다시 켜도 E6 카드와 함께 보임 ("보낸 질문은 그대로 남아 있어요"와 맞게). 다시 보내기에 성공하면 지움 (3-3 항목)
  - 대화를 만들기 전(H-1 단계)에 실패한 경우도 같음 — 다시 들어오면 빈 새 대화 화면에 실패한 질문과 E6 카드를 보여 줌
- 시간 초과 기준은 미정 → 임시 30초 (안건 #20 확정 후 변경)

### 4-8. 입력창

```
┌───────────────────────────────────────┐
│ ＋ │ 궁금한 점을 입력하세요      🎤 │
└───────────────────────────────────────┘   글자 입력 · 첨부 시 🎤 → ↑(전송)
```

- 입력창 안 아이콘도 누르는 영역은 48 이상
- 입력칸은 남는 폭에 맞춰 줄어들게 두고(최소 폭을 고정하지 않음) `＋` · 🎤/전송만 고정 폭 — 폭 320 · 360(작은 안드로이드) · 375(아이폰 SE)에서 전송 버튼이 밀리지 않는지 확인 (4-1 항목)
- 프로토타입은 `＋` · 🎤를 입력칸 밖에 두고 🎤 · 전송을 항상 함께 보여 줌 → 이 메모 방식으로 가고 팀에 공유 (10 항목)
- 여러 줄 입력 가능, 최대 높이 넘으면 입력창 안에서 스크롤
- 보낼 것이 있을 때만 전송 가능 — **글자가 있거나 사진 · 파일이 첨부돼 있으면** 🎤 자리에 전송 버튼, 둘 다 없으면(빈 글자 · 공백만 포함) 🎤. 최대 글자 수는 미정 (임시 500자)
- **Enter 동작**: 앱은 Enter = 줄바꿈, 보내기는 전송 버튼으로만 (여러 줄 입력이라 휴대폰 키보드의 Enter는 줄바꿈). 웹은 Enter = 보내기 · Shift+Enter = 줄바꿈
- 웹 한글 입력: 조합 중(`isComposing`)에는 Enter로 보내지 않음 (마지막 글자 중복 방지)

### 4-9. CB-04 첨부 메뉴

**보내기까지**

- `＋` → 바텀시트: 안내 "※ 처방전 · 약봉투는 홈의 [처방전 · 약봉투 분석하기]에서 올려 주세요." · [사진 촬영] · [갤러리에서 선택] · [파일에서 선택] · [취소]
- 배경을 누르거나 [취소] → 닫힘
- 사진 · 파일을 고르면 입력창 위에 미리보기 (× 로 빼기) → 전송하면 사용자 말풍선에 첨부 표시. 글자 없이 사진만 보내도 됨
- 올리기 전에 사진을 줄임 (긴 변 1600px 안팎 · Expo 기본 `expo-image-manipulator` — 최근 SDK에서 사용법이 바뀌었으므로 구현 때 사용하는 SDK 버전의 사용법 확인) — 데이터 · 시간 절약. 위치 정보(EXIF)는 담지 않음 (`expo-image-picker` 기본값 `exif: false`)
- **보낼 수 있는 파일** (임시, 9 항목): JPEG · PNG · HEIC · PDF, 10MB 이하. HEIC(아이폰 기본 형식)는 서버 · 웹에서 못 여는 경우가 많아 줄일 때 **JPEG로 바꿈**. PDF는 줄이지 않고 크기만 확인. **보내기 전에 앱에서 먼저 확인**해 막음 (서버 오류 413 · 415는 대비용, 3-6 항목)
- 사진 올리기(`attachments` API)가 실패하면 E6와 같게 — 사진도 실패한 질문처럼 다시 시도 (4-7 항목). 단 413 · 415(크기 · 형식)는 다시 시도로 풀리지 않으므로 E6 대신 사진 아래 안내 (3-6 항목). 사진 원본은 기기 저장소에 따로 보관하지 않고 사진 주소만 기억. **카메라로 바로 찍은 사진은 사진첩이 아닌 임시 파일**이라 앱을 나갔다 오면 지워질 수 있음 → 다시 시도할 때 파일을 찾을 수 없으면 "사진을 다시 골라 주세요" + [사진 다시 고르기]
- 함께 보낸 글자가 긴급 · 자해 규칙에 걸리면 사진도 올리지 않음 (4-6 항목)
- 권한: [갤러리에서 선택] · [파일에서 선택]은 시스템 선택기라 **권한 요청 없음** (안건 #11 "시스템 사진 선택기는 권한 불필요"와 같음). 권한이 필요한 것은 [사진 촬영]의 카메라뿐
- 카메라 권한 거부 시 안내는 OC-01-E2(카메라 권한) 패턴을 따를지 OCR 담당(채연)과 확인 (안건 #7)

**보낸 뒤 — 서버가 사진 종류를 판별해 세 가지로 답함**

| 서버 판별 | 챗봇 답변 | 형식 |
|---|---|---|
| **처방전 · 약봉투** (약이 여러 개 적힌 문서) · `imageResult: prescription` | "처방전(약봉투) 사진 같아요. 여러 약을 함께 점검하려면 분석하기에서 올려 주세요." + [처방전 · 약봉투 분석하러 가기] | `answerType: normal` + `action: open_analysis` → 버튼은 `onOpenAnalysis` 콜백 (OC-01, 채연 담당 화면). 챗봇에서 OCR · 분석을 따로 하지 않음 — Figma CB-04 "OCR 경로와 겹침 방지"와 같음 |
| **약 상자 · 약 한 개** (약 이름이 보이는 사진) | 약 이름을 읽고 **반드시 확인** — "사진 속 약이 **노바스크정 5mg** 맞나요?" [맞아요] [다른 약이에요] | `answerType: clarify` + `imageResult: drug` — E3 재질문 칩을 그대로 씀 (`clarify.items[0]`: key `drug`, options `["맞아요"]`, `allowInput: true`). [다른 약이에요]는 E3 [직접 입력]과 같음 (4-5 항목) — 직접 입력 칩 글자는 `imageResult: drug`이면 앱이 "다른 약이에요"로 바꿔 씀 (보통은 "다른 약 직접 입력"). 라벨은 "정보 확인", 문구는 E3 고정 문구("두 가지만 확인할게요")가 아니라 서버가 보낸 "사진 속 약이 ○○ 맞나요?" |
| **읽지 못함** (흐림 · 약 아님 · 글자 없음) · `imageResult: unreadable` | "사진에서 약 이름을 읽지 못했어요. 약 이름을 글자로 적어 주시면 답해 드릴게요." | `answerType: no_evidence` |

- **확인 후**: 사용자 말풍선에는 "맞아요"가 아니라 **약 이름**("노바스크정 5mg")을 표시 (대화 기록만 봐도 무엇을 확인했는지 알 수 있게). [맞아요] 또는 직접 입력한 약 이름으로 그 약에 대해 답함 — 사진과 함께 보낸 질문이 있으면 그 질문에, 없으면 약 설명(무엇에 쓰는지 · 어떻게 먹는지) + 후속 질문 칩
- 사진 약 확인은 **정책 ① 재질문 횟수(한 질문당 최대 2회)에 넣지 않음** — 확인 뒤에 약 종류 등을 또 물어야 할 수 있으므로. 판단은 서버 (8 항목)
- **확인을 꼭 받는 이유**: 약 이름을 잘못 읽고 그대로 답하면 **엉뚱한 약에 대한 안내**가 됨 (정책 ② "확인되지 않은 부분을 추측하지 않음"과 같은 원칙)
- 파일(PDF 등)은 사진과 같게 처리. 여러 장을 한 번에 보내는 기능은 이번 범위 밖 (한 번에 1장)
- 판별 · 읽기 방법은 백엔드와 협의 (8 항목) — 후보: 캠프 제공 모델(`gpt-4o-mini`, 사진 입력 가능)로 읽기, 또는 OCR(채연) 재사용
- 사진은 건강정보(민감정보) — 서버 보관 기간 · 파기 기준을 정해야 함 (9 항목, 정책 ⑨). 챗봇 대화 기록에는 사진 대신 "사진 1장" 표시만 남기는 방안도 검토

### 4-10. 음성 입력 (키보드 받아쓰기)

- 🎤 → 입력칸에 포커스, 키보드가 올라옴 (앱에서 키보드 마이크를 대신 누를 수는 없음)
- **처음 3번까지** 입력창 위 말풍선 안내: "키보드에 있는 🎤 버튼을 누르고 말해 보세요" + [마이크가 안 보여요] → 아이폰 · 갤럭시별 그림 안내 + [다시 보지 않기]
- 3번이 지나거나 [다시 보지 않기]를 누르면 안내 없이 키보드만 올림
- 길게 누르기는 고령 사용자가 찾기 어려워 쓰지 않음. 안내를 다시 보고 싶으면 [마이크가 안 보여요] 그림 안내를 내정보 > 도움말에도 둘 것을 제안 (내정보 담당과 협의)
- 안내를 봤는지는 기기에만 저장
- 삼성 키보드는 모델 · 버전마다 마이크 위치가 달라 실제 갤럭시 기기에서 확인 필요

### 4-11. 답변 읽어주기 (🔊, 신규)

- 답변 말풍선 아래 [🔊 듣기] → 재생 중 [⏹ 멈춤]
- 한 번에 하나만 재생 (다른 말풍선을 누르면 앞 재생 멈춤), 창을 닫거나 창 안 다른 화면(달력 · 목록)으로 가면 멈춤
- 읽는 범위: 라벨 → 본문. 출처 · 버튼 글자는 읽지 않음
- 속도 0.9배 (고령 사용자), 언어 `ko-KR`
- 답변 생성이 끝난 뒤에 버튼 표시
- 기기에 한국어 음성이 없으면 버튼을 숨김
- E4 · E5 카드도 읽기 대상에 포함
- 웹은 브라우저에 따라 온라인 음성(글자가 외부 서버로 전송)을 쓸 수 있음 → 정책에 한 줄 추가 필요

### 4-12. CB-02 대화 기록 · 달력

- 챗봇 창 안의 화면 — 창 머리: `<` 뒤로 (대화로) · "대화 기록" · × (4-1 항목)
- 안내 문구: "기록이 있는 날짜를 누르면 그날의 대화를 볼 수 있어요."
- 월 이동 `<` `2026년 9월` `>` — 다음 달은 이번 달까지만, 이전 달은 보관 시작일이 있는 달까지만
- 달력: 일 ~ 토 7칸. 기록 있는 날짜 = 연한 파랑 원 (누를 수 있음), 오늘 = 진한 파랑 원, 나머지 = 회색 글자. 범례 [● 기록 있음] [● 오늘]
- "기록 있음"은 **그날 시작한 대화**가 있는 날짜 (3-5 항목). 지난 대화를 오늘 이어 가도 오늘 날짜에는 표시하지 않음
- 오늘은 기록 여부와 상관없이 진한 파랑 원. 오늘 시작한 대화가 있으면 눌러서 CB-03으로, 없으면 누를 수 없음
- 보관 기간(기본 180일, 정책 ⑨)이 지난 날짜는 **기록 없음으로 표시** (Figma 기능설명서). 안내 문구에 "대화는 ○일간 보관돼요" 추가는 검토 중 → 우선 넣지 않음
- 창 안이라 하단 메뉴 없음 (Figma는 하단 메뉴 표시 — 플로팅 방식에 맞춰 Figma 수정, 8 항목)
- 처음 열면 이번 달. 기록이 전혀 없으면 달력은 보여 주되 "아직 대화 기록이 없어요" 안내
- 날짜 칸은 한 칸 44 이상, 날짜 글자 16 — 좁은 화면에서도 한 줄에 7칸이 들어가야 해서 4-1 항목 "누르는 영역 48 이상"의 예외
- 라이브러리 없이 직접 구현 (날짜 계산은 한국 시간 기준)

### 4-13. CB-03 날짜별 대화 목록

- 창 머리: `<` 뒤로 (→ CB-02) · "9월 16일 대화" · × · [전체 내보내기] 아이콘은 다음 단계라 숨김
- 안내 문구: "대화 제목은 내용을 바탕으로 자동으로 만들어져요. 눌러서 수정할 수 있어요."

- 카드 아래 글자 버튼: [제목 수정] (파랑) [삭제] (빨강) (이번 단계). [공유]와 카드 아래 공유 경고 상자는 다음 단계라 숨김

## 7. 기술 메모

### 7-1. 글자가 차례로 나오는 답변 (SSE)

- Expo SDK 52부터 기본 제공되는 `expo/fetch`가 응답을 조금씩 받는 기능(스트리밍)을 지원 → 외부 라이브러리 없이 가능. 구현할 때 앱 · 웹 모두에서 동작 확인
- React Native 자체의 `fetch`는 스트리밍을 지원하지 않으므로 `expo/fetch`를 써야 함

### 7-2. 1차 키워드 감지 (정책 ③)

- 범주: 가슴 통증 · 조임 / 숨쉬기 어려움 / 의식 저하 · 경련 / 한쪽 마비 · 말 어눌함 / 심한 출혈 / 입술 · 얼굴 · 목이 붓는 알레르기 반응 / 과다 복용 · 잘못 복용 → `emergency`
- 자해 · 자살 표현, 한꺼번에 먹는 양 · 위험한 양 질문 → `crisis`
- **"이미 먹음"과 "양을 물음"은 문장 끝 형태로 나눔** — 과거 · 완료형("먹었어요" · "먹었는데" · "삼켰어요") → `emergency` 과다 복용 / 가정 · 질문형("먹으면" · "먹어도" · "몇 알부터") → `crisis`. "과다 복용하면 어떻게 돼요?"처럼 키워드만 보면 과다 복용이어도 가정형이면 `crisis` (과다 복용으로 잘못 분류하면 [지금은 증상이 없어요] 칩도 사라져 사용자가 빠져나갈 방법이 없음)
- 예시 — 이미 먹은 경우("많이 먹었어요" · "과다 복용했어요" · "한꺼번에 먹었어요") → `emergency` / 먹을 양을 묻는 경우("몇 알 먹으면 위험해요?" · "한꺼번에 먹으면 어떻게 돼요?") → `crisis` (Figma E4 · E5 기능설명서)
- 두 범주에 동시에 걸리면 **둘 다 표시** (E4 카드 + 아래 E5 안내, 4-6 항목). 한 범주에 걸렸다고 다른 범주 검사를 멈추지 않음
- 과다 복용 · 잘못 복용 규칙은 따로 표시 (`SafetyInfo.overdose`) — [지금은 증상이 없어요] 칩을 숨기는 데 씀 (4-6 항목)
- 안전 모드(24시간)에서는 약의 양 · 한꺼번에 먹기 질문을 계속 `crisis`로 봄 (4-6 항목)
- 키워드 목록의 출발점: 회의용 프로토타입 규칙 — `emergency` 가슴 · 숨쉬 · 호흡 · 의식 · 마비 · 어눌 · 출혈 · 입술 · 얼굴이붓 · 과다복용 · 많이먹었 · 한꺼번에 / `crisis` 죽고 · 사라지고 · 자살 · 자해 · 살기싫. 여기에 위 "이미 먹음 / 양을 물음" 구분과 동시 해당 처리를 더함
- 놓치지 않는 쪽 우선 (오탐 허용)
- 비교 전에 **띄어쓰기 · 공백 · 문장부호를 없앰** ("가슴이조여요" · "가슴이 조여요!" 모두 감지)
- 규칙마다 **시험 문장**을 둠 — 감지해야 할 것 / 감지하지 않을 것 (예: 감지 "약 먹고 가슴이 조여요" · 비감지 "혈압약은 아침에 먹나요?"). 오탐 허용이므로 "가슴 통증에 먹는 약은 언제 먹나요?"처럼 애매한 문장은 감지돼도 됨 — [지금은 증상이 없어요]로 이어서 답을 받음. 규칙을 고칠 때마다 자동 시험 (7-8 항목)
- 과거형 · 가정형도 일단 안내 → [지금은 증상이 없어요]로 재개
- 걸린 기록은 시각 · 규칙 이름만 (대화 원문은 남기지 않음)
- 키워드 목록을 앱에 넣을지 서버에서 받을지 미정 → 우선 `src/safety/`에 두고 한곳에서 관리

### 7-3. 약 이름 뒤 조사 처리

- 약 이름 · 질환명처럼 바뀌는 말 뒤 조사는 **받침을 보고** 고름: 과/와 · 은/는 · 이/가 · 을/를 · 으로/로
- 한글로 끝나면: 마지막 글자의 받침 유무를 유니코드로 계산 (`(글자코드 − 0xAC00) % 28 ≠ 0` 이면 받침 있음). "으로/로"는 받침 ㄹ이면 "로"
- 영문 · 숫자로 끝나면 읽는 소리 기준 (예: "250mg" → "밀리그램" → 받침 있음 → "은"). **자주 나오는 끝말만 표로** 정함 — mg · g · mL · 숫자 0~9 (영 · 일 · 이 · 삼 …). 한글 끝말(정 · 캡슐 등)은 위 계산으로 처리
- 표에 없는 끝말은 조사가 필요 없는 문장으로 바꿔 씀 (예: "○○과(와) △△은(는)" 대신 "○○ · △△ 두 약은")
- `copy.ts`에 함수로 두고 모든 문구에 사용. 서버가 만드는 답변 문구에도 같은 규칙 요청 (8 항목)
- 프로토타입 E2 답변 "엔티심바정20밀리그램과(와) … 250mg은(는)" · RG-02 "○○연질캡슐"은(는)" 처럼 괄호로 남기지 않음

### 7-5. 시간 · 날짜 기준

- 현재 시각은 **`utils/now()` 한곳에서만** 가져옴 — 개발용 진입 화면의 "오늘 날짜 바꾸기"가 모든 화면에 적용되게 (5 항목)
- 날짜 계산("오늘" · 달력 · "5일 전")은 기기 시간대와 상관없이 **한국 시간** 기준
- 계산 방법: 시간대 이름(`Asia/Seoul`)으로 바꾸지 않고 **UTC에 9시간을 더해** 계산 — 앱의 자바스크립트 엔진(Hermes)은 기기 · 버전에 따라 시간대 지정 지원이 불완전할 수 있음. 한국은 서머타임이 없어 +9시간 고정으로 항상 맞음

### 7-6. 기기 저장 (AsyncStorage)

- 저장하는 것: 실패한 질문 (4-7 항목) · 받아쓰기 안내를 본 횟수 (4-10 항목) · 안전 모드 끝나는 시각 `safetyModeUntil` — 서버에서 받은 값과 앱에서 `crisis`를 감지한 "지금 + 24시간" 중 늦은 쪽 (오늘 대화 찾기가 실패했을 때 판단용, 4-6 항목) · 서버에 보내지 못한 긴급 기록 (원문 없음, 보내면 지움, 4-6 항목)
- 안전 모드 시각 · 보내지 못한 긴급 기록은 **로그인한 사용자별로** 저장하고, 로그아웃 · 탈퇴 · 민감정보 동의 철회 때 지움 (철회 때 서버 기록도 즉시 지우므로 기기 값도 남기지 않음, 4-6 항목) — 같은 기기를 다른 사람이 쓸 때 이전 사용자의 안전 모드가 남지 않게
- 실패한 질문에는 건강정보가 들어 있음 → **다시 보내기에 성공하면 바로 지우고, 7일이 지나면 자동으로 지움** (웹은 브라우저 저장소에 암호화 없이 남아 공용 PC에서 보일 수 있으므로 **하루**). 로그아웃 · 탈퇴 · 민감정보 동의 철회 때 지우는 것은 내정보 담당과 맞춤 (8 항목)
- 서버 대화 기록을 기기에 따로 복사해 두지 않음 (다시 들어오면 H-2로 불러옴)

### 7-7. 요청 ID

- `clientRequestId`는 Expo 기본 `expo-crypto`의 `randomUUID()`로 만듦 (앱 · 웹 모두 동작)
- 한 질문에 하나. 다시 시도 · H-1 → (사진 올리기) → H-3 모든 단계에 같은 ID (3-5 · 4-7 항목)
